## 1. 取证

- 写盘点：`StateManager::get_next_chapter_number`（manager.rs）里的 `let _ = bootstrap_structured_state_from_markdown(...)`——**返回值被丢弃的纯副作用调用**。书架接口（`GET /api/v1/books` 对全部书并行取摘要）经此链路，legacy 书（无状态四件）首读即被物化出 `story/state/{manifest,current_state,hooks,chapter_summaries}.json` 四件。
- **TS 同名链不写**：`packages/core/src/state/manager.ts` 的 `getNextChapterNumber` 只算 `resolveDurableStoryProgress`（纯派生）——两腿同名链不对称，Rust 是孤立漂移。
- 历史脉络：784 号台账实证「每读必写」（9ms/读）→ 785 号折衷为「首读 ensure 一次 + 快路径零写」→ 787 号性质锁（`e2e_read_chain_zero_write.rs`）以**两相编码**给首读 ensure 留了 by-contract 豁免（warmup 相断言四件出现、steady-state 相断言零写）。
- 生产者全景：状态四件的全部生产调用=write_next `save_truth_files`（写路径 ensure，带「TS syncLegacyStructuredStateFromMarkdown」对齐注释）、memory_retrieval（带「TS bootstrapStructuredStateFromMarkdown(...).catch」逐字对齐注释——**TS 镜像面，不动**）、读端点（本轮删除）。没有任何消费方依赖「读端点先物化过」：全部四件读取方要么自己 ensure 要么容忍缺失（`read_structured_state` Option / tolerant 读）。TS 腿 legacy 书从来没有读端点 ensure，写链工作正常——785 号当时标注的「legacy 可用性所依，load-bearing」实际不 load-bearing。

## 2. 定线

**读端点零写**（推翻 784/785 折衷的读副作用，对齐 TS 同名链）：

1. GET 读请求不应有写副作用——用户只浏览不改，盘上不该多出一堆生成文件（备份/同步/回收站对账视角的幽灵变化）；并发首读同一本 legacy 书还会双 bootstrap 并发写四件（原子写防撕裂但双写+mtime 抖动，1678 号对跑「恰好四件」钉定的根源）。
2. 「每读必写 → 首读一次」的性能病灶与折衷随副作用一并消失——读取面不再有任何写，比快路径更省。
3. 两腿对称：TS 读取面不写是既成事实，Rust 对齐。
4. 下一次写（write-next / 记忆检索 / 状态保存）时 ensure 照常物化——legacy 书的可用性不受影响。
