# 775 号：信任路由容器形态误拒修复——活体探针抓获（768 信任校验与载入器发现语义不一致）

> 活体验证纪律的又一次胜利：768/769 信任链此前只有单测（直连形态）+
> 路由单元缺位——真实引擎端到端探针第一跑即抓获真缺陷。

## 一、缺陷实锤（活体探针三层证据）

1. **探针形态**：真引擎 + `INKOS_SKILL_DIRS=/tmp/…/ext`（容器目录，技能
   在 `ext/my-probe-skill/SKILL.md`——**最常见的真实用法**：用户把 env
   指向含多个技能的父目录）；
2. **GET /skills**：载入闸正确（external 诊断待确认 + 技能未入列 + user
   惯例目录默认信任不受影响）——768 载入闸本身无恙；
3. **POST /skills/trust**：`400 "Skill source directory has no SKILL.md"`
   ——信任路由硬性要求根上有 SKILL.md，而载入器 `discover_skill_dirs`
   接受"根无 manifest 但两层内子目录有"的容器形态。**769 一键确认对
   容器形态必红**，且 POST 失败后诊断仍在、用户无从下手。
   附带活体证据：撤销链（DELETE + entries 空）与信任库文件写入均正常。

## 二、修复（双栈同构）

- 新可装载判定助手：TS `hasSkillManifestDirectOrBelow` / Rust
  `has_skill_manifest_direct_or_below`——**与载入器发现语义完全一致**
  （根上有 SKILL.md，或两层内子目录有，对齐 `discoverSkillDirs` 深度 2）；
- 信任 POST 校验改用该助手（错误码/键不变，消息更准确：
  "no loadable SKILL.md (direct or within 2 levels below)"）；
- 实施插曲：core 顶层精选导出表再次漏项（768 同款坑第二次）致 studio
  tsc 红——已补 `hasSkillManifestDirectOrBelow` 导出。

## 三、回归锁（双栈四形态）

- TS/Rust 各 4 测：直接形态 true / **容器形态 true（768 误拒回归锁）**/
  两层外才有 false（深度语义一致）/ 空目录 false。

## 四、活体复验（修复后全链）

POST（容器形态）→ `ok:true` + 信任条目落库 → GET /skills：
`my-probe-skill` 载入 + pending 诊断清零 → DELETE 撤销 → 技能卸载回
待确认态。全链三步活体通过。
