# 777 号：三面 ops 死字段清偿（676b 产品线索定界收口）

> 676b 备案的「支线板/情感弧线/角色矩阵随章自动更新（schema 预留未实现）」
> 本轮全面勘察定界：三面面板**已有**真实更新机制（settler UPDATED_* TAG
> 全量替换路径），delta 里的 subplotOps/emotionalArcOps/characterMatrixOps
> 三字段自 fork 引入以来**无任何 apply 消费端**——属死字段而非待实现功能。
> 处置=清偿而非补 apply（详见「一、定界」）。

## 一、勘察与定界（为什么删而不是实现 apply）

链路全景（Rust 产品引擎侧）：

1. `settler_prompts.rs` JSON 输出示例每章向模型索要三面空数组（token 浪费，
   且暗示模型可以影响三面面板——实际产出被静默丢弃）；
2. `RuntimeStateDelta`（models/runtime_state.rs）携带三字段
   （`Vec<HashMap<String, serde_json::Value>>`）；
3. `hook_arbiter.rs` 仲裁后原样透传；
4. **全仓 grep 双形态（snake_case/camelCase）确认零消费端**——无 apply、
   无落盘、无 API 暴露（src-tauri/scripts 亦零命中）；
5. 三面面板真实更新链：settler 输出 `UPDATED_SUBPLOTS` /
   `UPDATED_EMOTIONAL_ARCS` / `UPDATED_CHARACTER_MATRIX` TAG →
   `settler_parser.rs` 提取 → `build_persistence_output.rs` 全量替换落盘
   （676b 所述 writer.ts TAG 路径的 Rust 同构物）。

决策依据：

- **实现 apply = 为死字段续命且制造双写者**：TAG 路径是全量替换语义，
  ops 是增量补丁语义，两者写同一批面板文件会产生竞争写者；且 676b 立项
  触发（真实产品需求）从未到位，review-matrix 七场景与用户面均未表达
  「需要第二条面板更新通道」。
- **TS 侧佐证**：上游 2.0 基底重构后 `RuntimeStateDeltaSchema`（zod
  `.strict()`）与 settler-tool 工具 schema 均无三面字段——TS 侧已先行
  淘汰同一批字段，Rust 侧持有它们是 fork 时代遗留，双栈 delta 契约因此
  存在潜在 strict 解析分歧面（TS strict 拒多余键）。
- 清偿收益：每章省 prompt token（三行示例+模型镜像输出三行）；消除静默
  丢数据面；双栈 delta 形态对齐。

## 三、兼容性设计

- serde 默认未知键忽略：旧盘上/旧模型输出中的三键读取零影响（无
  `deny_unknown_fields`）；
- delta 不持久化（结算链内存构建后 apply 进 state 文件），无盘上形态
  迁移问题；
- 向另一侧的 strict 消费（若未来出现）反而因键减少更安全。

## 五、教训

1. **schema 预留字段是负债不是资产**：676b 把三面 ops 记为「待实现产品
   功能」，本轮勘察证明真实机制（TAG 路径）一直在位——「预留未实现」的
   正确处置多数时候是删除，等真实需求到位再按需设计（届时未必是这个
   形态）；为死字段补消费端只会固化一个无需求支撑的设计。
2. **死字段审计的判定标准=消费端 grep 双形态全仓零命中**（676b 已给出
   结论，本轮用 snake_case+camelCase 双 grep+src-tauri/scripts 扩面复核
   才动手）；「schema 有、prompt 索要、中间层透传」三层齐备极具迷惑性，
   唯独第四层（落盘/暴露）缺失。
3. **删除类变更的回归锁是「旧形态仍被接受」而非「新形态被拒绝」**：
   双探针（旧键容忍+最小新形态可解析）+ golden input 保留三键，把向前
   兼容语义显式钉死，防止未来有人以「严谨」为名加 deny_unknown_fields
   打破旧输出兼容。
