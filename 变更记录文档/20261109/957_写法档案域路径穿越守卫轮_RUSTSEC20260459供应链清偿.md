## 一、缺陷面定型（按族扫三站双端 + 读面纵深）

- **站 1 档案写面**：`POST /api/v1/style-profiles` 的 `name` 直拼
  `dir.join(format!("{name}.json"))`（Rust ops_routes.rs）/ `join(dir,
  \`${name}.json\`)`（TS server.ts）——`name="../../books/b1/book"` 覆写
  项目内任意 .json（secrets/inkos.json/他书 book.json=配置投毒二阶），
  更深 `../` 写出项目根。双端同患。
- **站 2 绑定探针**：`PUT /api/v1/books/:id/style-binding` 的
  `profileName` 直拼存在性探针 `join(root,".inkos","style-profiles",
  \`${profileName}.json\`)`——穿越名=盘外文件存在性预言机（200 绑定落盘
  vs 404 区分任意路径存在性），且名字写入 style_binding.json 由 composer
  读面二次拼路径（**存储型穿越**）。双端同患。
- **站 3 拆书写面**：`POST /api/v1/books/:id/deconstruct` 的 `name` 直拼
  `{name}.md`（chapters 守卫之后）——穿越名写出项目根。双端同患。
- **composer 读面纵深**（Rust `load_style_binding_entry`/TS 版已随上游
  删除）：绑定文件是用户可编辑数据/旧版穿越名可落盘——`profile_name`
  直拼 `story/style-profiles/{name}.json` 读出项目外任意 .json 进写作链。
- **同族已守卫对照**（判据来源佐证）：genres 双站有 `/[/\\\0]/.test+
  includes("..")` 守卫、series 有 `isValidSeriesId`、books id 有 201 号
  `is_safe_book_id` 中间件+点状校验——style 域是漏网三站。
- **B 面备案（功能孤树，非安全）**：composer 读 `bookDir/story/
  style-profiles/`（340 号设计）而唯一写面是 `root/.inkos/style-profiles/`
  ——两树不一致+`resolve_style_binding` 以 `sourceName`（样本源名）匹配
  `profileName`（档案名），绑定注入特征或恒空。需产品语义定案（读树应为
  哪棵/匹配键应为哪个），957 不擅动，留 958 备案。

## 二、双端修复（复用 201 号同一判据源，零新轮子）

- 三站统一过 `crate::utils::is_safe_book_id`（Rust）/`isSafeBookId`
  （TS，books id 段同款：非空≤120 无分隔符/控制字符/引义符/`..`）——
  同一真源=201 号 books/projects id 段守卫；错误消息逐字对齐（站 1/2
  `invalid profile name`、站 3 `invalid export name`）、次序对齐（站 3
  chapters 守卫在前）。
- composer 读面：不规范名一律零打扰跳过返回 None（与既有「缺失/解析失败
  返回 None」同契约——不做 400，读面语义是注入缺失不打扰）。
- Rust deconstruct 顺带 trim 对齐：TS `body.name.trim()` 后用 trim 值而
  Rust 旧版 `.filter(|n| !n.trim().is_empty())` 保留原串——文件名可带首
  尾空白与 TS 产物名不同源（双端一致性缺陷，测试锁）。
