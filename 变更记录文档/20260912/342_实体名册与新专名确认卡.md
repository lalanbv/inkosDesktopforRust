- 规划依据：[328 规划](../20260911/328_对标调研分析与改进规划.md) G7b（WNW W6 实体名册+新专名确认的采纳）
- 范围说明：本号为 G7b 的**契约层**（名册 truth 类目 + 候选提取 + 三选比对 + 确认卡
  渲染，全纯函数）；settle 链自动比对接线与聊天确认卡 UI 为后续编号（对齐 G3 的
  336/337 拆批先例）。

## 做了什么

1. **名册 truth 类目** `story/entity_roster.md`（作者可手改，每条一节 + 平铺
   key: value 行）：`name` 规范名 + `aliases` 别名 + `kind`（person/place/faction/
   item/other，非法归 other）+ `registeredAt` 登记章。
   `parseEntityRoster` / `renderEntityRoster` 双端互逆（无名节跳过、手改容错）。
2. **候选提取** `extractCharacterCandidates`：从章摘要 characters 列（settle 链
   LLM 从正文提取的出场人物——现成的高质量专名信号）拆分提取，分隔符
   `,，、;；/`（不含 `·`——约翰·史密斯类名字不被拆散）、去重保序、剔除停用词
   （无/none/未知…）。
3. **三选比对** `resolveRosterCandidates`（确定性决策，golden 锁死）：
   - 精确命中 name/aliases（大小写不敏感）→ 已登记不出卡；
   - **包含关系**（候选含规范名或被规范名包含，短者 ≥2 字——"青镇儿"/"林小哥儿"
     类昵称后缀）→ alias（指向规范名，medium）；
   - **编辑距离 ≤1**（自实现 Levenshtein，双端一致）→ typo（指向规范名，high）；
   - 其余 → new-entity（low）。
   向量先行抓出实现顺序缺陷：初版"编辑距离优先"会把儿化昵称"青镇儿"误判为
   "青镇"的笔误——调整为包含关系（昵称）优先于距离（笔误）。
4. **确认卡渲染** `renderRosterConfirmationCard`：人话三选列表（"X → 疑似 Y 的
   笔误？"/"可能是 Y 的别名？"/"新实体？"），聊天确认卡与审计注入共用；空卡
   undefined。
5. **共享 golden 向量** `entity-roster-vectors.json`（16 例：解析 3 + 渲染 1 +
   候选提取 1 + 三选 4[混合排序/精确与别名跳过/大小写命中/空名册全新] + 卡渲染
   双语 2 + 契约冻结）。TS 6 项 + Rust 差分 6 项（第十一个共享守门域）。
