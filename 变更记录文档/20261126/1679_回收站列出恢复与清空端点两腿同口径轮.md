## ① 取证（先红）

**回收站只进不出**：基线 9f08cda0 实查两腿的路由面——`server.ts` 里回收站只出现在两处：备份的排除过滤器（1676 号）与删书路由的 `trashBook` 调用；产品引擎只在 `rollback_to_chapter` → `move_into_batch`。没有任何列出 / 恢复 / 清空的路由。进了回收站的内容只能靠文件管理器手工挪回来。

**回收站的两级布局**（1676 号立的，本轮只读它）：

- 章级：`{bookDir}/chapters/.trash/`。平铺的章文件（重名时带 `-2`、`-3` 后缀）与回滚批次 `rollback-{yyyyMMddHHmmss}-{target}[-n]/`（书内相对路径原样）。
- 书级：`{projectRoot}/.trash/books/{bookId}--{yyyyMMddHHmmss}[-n]/`。两腿**共用这一个目录**（桌面默认产品引擎、Node 是回退，同一个项目根），但形态不同：产品引擎删的书根上是 `book.json`，Node 腿删的书是 `work.json` 加 `source/`（没有清单的孤儿目录只有 `source/`）。

**先红**：Node 腿先写测试——core 15 条、路由 8 条，端点落地前红（路由 404、core 函数尚不存在）。产品引擎的测试与实现同批写，共享向量那条当场抓到一处真缺陷（`compact_to_iso` 把日字段取成 8 位，所有时刻都判成不存在）。

## ② 设计定线

六条路由，两腿同一条契约：

| 路由 | 请求 | 响应 |
|---|---|---|
| `GET /api/v1/trash/books` | — | `{ entries: BookTrashEntry[] }` |
| `POST /api/v1/trash/books/restore` | `{ entry }` | `{ ok, entry, bookId }` |
| `POST /api/v1/trash/books/purge` | `{ entry }` | `{ ok, entry }` |
| `GET /api/v1/books/:id/trash` | — | `{ entries: ChapterTrashEntry[] }` |

条目字段：书级 `entry / bookId / trashedAt / bytes / fileCount / title`；章级 `path / originalPath / batch / bytes / modifiedAt / trashedAt`；找回的章文件带 `chapter: { number, meta }`（该登记进目录的条目），其余文件 `chapter: null`。

错误面：400 `INVALID_TRASH_REQUEST`（请求不成形、路径越界或不是回收站布局）、404 `TRASH_ENTRY_NOT_FOUND`、409 `TRASH_TARGET_EXISTS`（带 `conflicts`：已在原位的原路径）、500 `TRASH_IO_ERROR`（盘上的操作失败）；书不在 → 404，与书详情同形。

取舍：

1. **恢复是把文件找回来，不是撤销**。只把条目移回原位；状态与快照不动。目标已在原位 → 409，一个字节都不覆盖，一个都不移（整批全有或全无）。
2. **找回章文件必须登记进章节目录**，否则这一章在界面上看不见；Node 腿更是直接被进度守卫判成孤儿，整本书在书架接口上 500。目录里已经列着这一章就不动它。条目来源：回滚批次里存着回滚前的目录，就取这一章原来的条目（状态、词数都是回滚前的）；取不到按文件现做，与索引重建同口径。
3. **先写目录、后搬文件**。目录写不下来（磁盘满最典型）就什么都不搬，回收站里原样留着、书架照常，重试即可。反过来做的话文件回位而目录不列——重试又撞上「条目不在」，没法自愈。这条是复核时发现的，初版是先搬后写。
4. **同章双形态一起回到原位时**（旧命名的章与重写后的正典章都在同一个回滚批次里）目录条目跟随读侧会打开的那一个文件：正典优先、同类内文件名序小者，与索引重建同一个裁决。一个章号永远只有一行。
5. **书级各腿只认自己删出来的形态**，另一条腿的条目 → 404。把另一种形态搬进本腿的书根，得到的是一本坏书。
6. **清空只删列出来的条目**：符号链接、认不出的布局不碰——删掉的一定是界面上列过的。全部清空之后回收站目录里可能剩看不见的残余。这条也是复核时收紧的：初版 `{ all }` / `{ batch }` 整目录删，返回的 `removed` 却只数列出来的条目，数字不对账。
7. **条目识别是两腿共用的纯函数**，向量表两端同读（`packages/studio/src/__tests__/golden/trash-entry-vectors.json`，产品引擎 `include_str!`）。路径里不许有 `..`、空段、反斜杠、NUL——调用方拿到的原路径一定还是书内相对路径。
8. **时间必须真实存在**：`b1--20261301000000`（月 13）不是条目。两腿都是「折算成毫秒再折算回来逐位相同」这一条判定。
9. **排序两腿恒等**：`trashedAt`（没有则 `modifiedAt`）降序，再路径升序。Node 腿走码点序（`compareByCodePoint`，854 号立的比较器，本轮起导出），不用 `<`——UTF-16 码元序在增补平面字符与全角标点之间是反的。
10. **书级没有 `{ all: true }`**：批量真空删除整本书风险更高，第一批不做，逐条清空。
11. **符号链接不是条目**：列不出来、找回不了、清空不碰，不跟着链接走到回收站外面去。

## ⑥ 顺带发现与立案

- **跨腿排序口径是一族**：Node 腿还有按 `<`（码元序）排、结果又与产品引擎并排比的列表（例如 `server.ts` 里的 `documents.sort`）。只有增补平面字符与 U+E000–U+FFFF（含全角标点）相邻时两腿次序相反，影响面小。本轮只把回收站条目表改对，没有全仓扫。
- **`is_js_whitespace` 含 U+0085**：Rust 的 `char::is_whitespace` 算 NEL，JS 的 `\s` 不算。既有工具函数，影响面可忽略，备案。
- **列出时条目消失**：`readdir` 与 `lstat` 之间文件被别的进程拿走，两腿都是 500。回收站没有并发写方，不处理。
- 1678 号立案的三条仍开着：产品引擎读取面写盘、导出校验严格度、旧版可选真相文件的恢复口径。
