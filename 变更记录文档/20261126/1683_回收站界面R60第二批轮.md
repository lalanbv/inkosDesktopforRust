# 1683 号：回收站界面——书级与章级面板、恢复与真空删除两步确认（R60 第二批）

> 日期：2026-11-26 ｜ 类型：功能补齐轮（studio UI）+ 对跑夹具竞赛修复
> 定位：R60 第二批。1679 号把回收站的六个端点补齐了（两腿同契约），但界面上一条找回入口都没有——删书、驳回了章，只能靠文件管理器手工挪。本轮补 UI 消费面；保留期（多少天自动清空）仍是独立出口，本轮未动。

## ① 取证

**端点在、界面缺**：1679 号的六条路由（`GET /api/v1/trash/books`、restore/purge、`GET /api/v1/books/:id/trash`、restore `{path}|{batch}`、purge `{path}|{batch}|{all:true}`）两腿同契约且对跑钉死；界面上搜不到任何消费——删除书的两处入口（Dashboard 书卡菜单、BookDetail 危险按钮）确认后书就「消失」，没有去向提示也没有找回路径。

**UI 惯例取证**（全部复用既有件，不引入新模式）：面板外壳 = `BackupPanel` 的 `rounded-lg border` 卡；确认弹层 = `ConfirmDialog`（danger variant，Escape/遮罩取消）；双语 = 组件内 `tr(中, 英)`；在途互斥 = BackupPanel 955 号的 `busyRef` 惯例；列表竞态 = 1008 号 seq latest-wins；书架刷新 = `invalidateApiPaths(["/api/v1/books"])`；交互测试 = testing-library + `// @vitest-environment jsdom`（BackupPanel.interaction.test 先例）。

## ② 设计定线

- **书级 `TrashPanel`**：Dashboard 挂在 BackupPanel 之后。头部常显（计数徽标 + 说明），「查看回收站」展开条目区。条目行 = 标题（无标题回落 bookId）、删除时间（`trashedAt` 本地化）、文件数、大小；行内「恢复」（可逆操作，不设确认）与「彻底删除」（danger 两步确认）。恢复成功 → `invalidateApiPaths(["/api/v1/books"]) + 面板重列；409（书目录已被同 id 新书占用）/404（条目已被清）→ 面板错误条显示服务端原文并重列，不假清空。
- **章级 `ChapterTrashPanel`**：BookDetail 章节区之后挂载，`onRestored={refetch}`（找回的章服务端已登记进章节目录——1679 号语义，前端只需刷新）。展开时拉列表；条目按回滚批次分组（列表本身已排序，相邻同批聚合）：批次头 = 批次名 + 批次时间 + 「整批恢复」「整批删除」；行内 = 「恢复」「删除」（行级删除同样两步确认）；底部「清空回收站」= `{all:true}`。真空删除影响章节面时确认后才触发 `onRestored`。
- **真空删除全部两步确认**：四种形态（书级彻底删除、章级行级删除、整批删除、清空回收站）统一走 `ConfirmDialog` danger——确认前不发请求。恢复不设确认（可逆）。

## ③ 测试与变异

- **先红**：两个 interaction 测试文件先写，组件不存在时 import 解析失败=红（12 条最终绿：书级 6、章级 6）。另跑 `Dashboard.test.tsx` 防挂载回归。
- **变异 5 个**，全部阵亡：
  | 变异 | 咬住的测试 |
  |---|---|
  | 书级恢复后不失效书架列表（去 invalidateApiPaths） | 恢复刷新书架 |
  | 章级恢复后不回调 onRestored | 恢复后刷新章节列表 / 清空后刷新 |
  | 整批恢复退化成单条（`{batch}`→`{path}`） | 整批恢复一次请求 |
  | 清空回收站退化成单条（`{all:true}`→`{path}`） | 清空两步确认 |
  | 书级彻底删除跳过确认（直接 purge） | 确认前不发请求 / 取消不发请求 |
- **一个先存活的变异**：章级行级「删除」跳过确认——初版测试只覆盖了「清空回收站」的两步，行级没有断言。按纪律补测试而不是接受变异：补「行级删除两步确认」用例（确认弹层开、purge 未发、确认后 `{path}` 精确、重列后该条消失）→ 重放变异 1 红 → 还原后 12 绿。
