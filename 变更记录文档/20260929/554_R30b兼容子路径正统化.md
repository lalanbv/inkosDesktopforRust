## 一、实施内容

### 现状实锤（正统化方案的证据链）

- **上游 0.87 主入口不含四函数**：streamSimple/completeSimple/getModel/getEnvApiKey 全部只在 deprecated 的 `./compat` 子路径（头注明言"随 coding-agent ModelManager 迁移删除"）。正统面 = `providers/all` 的 `getBuiltinModel`（静态目录读）+ `createModels()`/`Models`（ModelManager 用重型对象）+ per-API 模块直接导出的 `StreamFunction`。
- **compat 分发链解剖**：`streamSimple = normalizeContext → builtin provider 判定（provider 目录含同 api 模型才命中）→ Models.applyAuth → api-registry → per-API 函数`。对**本仓形态**（无凭据库、model 自描述 baseUrl、`options.apiKey` 显式在场）中间两层为空操作：`applyAuth` 的 `options.apiKey ?? auth.apiKey` 显式优先、本仓 provider 无 auth.baseUrl/自定义 headers、`createModels()` 无 credential store。
- **apiKey 链实证**：pi-agent-core `agent-loop` 每 streamFn 调用显式传 `apiKey: resolvedApiKey`（`getApiKey` 回调 || `config.apiKey`）；provider.ts 走 `client._apiKey`；compaction 走 secrets/env 显式解析——三调用点显式在场，compat `withEnvApiKey` env 兜底在本仓是冗余第二保险。**活路径**仅 agent-session 的 `getApiKey` 回调（config.apiKey 缺失时查上游 envMap，如机上有 OPENAI_API_KEY 的开发机）。

### 改造面

| 上游 compat 函数 | 正统替代 | 消费点 |
| --- | --- | --- |
| `getModel` | `getBuiltinModel`（`@earendil-works/pi-ai/providers/all`，签名相同纯换源） | service-resolver / agent-session |
| `streamSimple`/`completeSimple` | **自持 `llm/pi-dispatch.ts`**：`normalizeContext`（主入口）+ 按 `model.api` 分发 per-API 模块直接函数（openai-completions / openai-responses / anthropic-messages 三键=本仓 preset 全集，未知清晰抛错） | provider / pi-stream / session-compaction |
| `getEnvApiKey` | **自持 `llm/pi-env-keys.ts`**：`getApiKeyEnvVars` 全表镜像 + anthropic AUTH_TOKEN 跳过特判 | agent-session / session-compaction |

### 与上游行为的差异（全部备案于模块头注）

1. builtin provider 分支（provider 级 OAuth/ambient 凭据注入）不镜像——本仓全部自管 key。
2. `withEnvApiKey` 流内 env 兜底不镜像——三调用点显式 apiKey 在场（上述实证）；env 兜底语义由 pi-env-keys 在调用侧显式承接（getApiKey 回调/compaction fallback 两处）。
3. cloudflare-ai-gateway 特判、api-registry 自定义注册不镜像——本仓 provider 集不含/未使用。
4. pi-env-keys 不移植 google-vertex/amazon-bedrock 环境凭据特判（本仓 provider 集不含）与 Bun sandbox `/proc/self/environ` 回退（Node 桌面形态 process.env 恒可用）；其余 36 键 env 表全量镜像（纯数据表，单测锁定本仓 provider 集八键+anthropic 优先序特判）。

## 三、教训与备案

1. **deprecated 子路径的迁移裁决靠"行为链解剖"而非"导出对照"**：上游正统替代（Models/Provider 体系）与本仓消费形态（自管 key/自描述 model）差异巨大，直接套用反而引入凭据体系依赖；解剖 compat 分发链逐层证明"中间层对本仓为空操作"后才得出"per-API 直接函数+normalizeContext 等价"的最薄形态。
2. **自持副本的取舍线=漂移风险 vs 消费面**：getEnvApiKey 的 36 键表是纯数据（全量镜像+单测锁定）；而 vertex/bedrock ADC 文件检查、Bun /proc 回退是行为分支（不镜像+备案本仓 provider 集不含）——数据镜像、行为裁剪，两者备案方式不同。
3. **env key 的事实双通道**：本仓 `getServiceApiKey` 按 service 名派生 env 名（`MOONSHOT_API_KEY`），上游 envMap 按 piProvider 名（`moonshotai`）——两通道键名空间不同且并存；compat 移除后上游通道仅存于 getApiKey 回调一处（自持承接），secrets.json 仍是第一优先。
4. **mock 面跟着 import 面走**：548 号教训（"mock 须指向消费方实际 import 面"）在本轮再验证——四测试文件的 mock 目标全部随源迁移，hoisted 共享桩组形态不变只换挂载点。
5. R30b 清偿后 v6 Pi 对标备案全部关闭（R30/R30b/R31/R32/R33 五项收官）；compat 删除时钟风险出清，剩余 R34+（R36/R37 施工图 546 号）与 R38b 顺延的 TS buildChatToolSet（packages/core 解冻后可排）。
