## 做了什么

1. **settler 提示词 7 类词表双端**：输出格式示例的 upsert/newHookCandidates
   各加 `"kind"` 字段（emotion/suspense 与示例 type 语义对齐）+ 新增规则 9
   （kind 只能从 promise/suspense/crisis/artifact/information/emotion/
   worldview 选一，归类不了就省略）。**双端逐字机械比对验证一致**
   （Python 脚本去 format!/模板转义后逐行 diff=0；4 处差异全为转义伪差）。
   既有提示词相关测试/eval 锚点全绿（substring 锚定，未受影响）。
2. **LLM 边界容错归一化双端**：`parseSettlerDeltaOutput`/
   `parse_settler_delta_output` 在 schema 解析前对 upsert 条目与
   newHookCandidates 的 kind 值经 `normalizeHookKind` 别名表归一——
   **词表外的值删除（undefined）而不是拒收整个结算增量**（一次 LLM
   手误不再拖垮整章结算；宿主是归一者，schema 保持严格）。
3. **候选链全透传双端**：`NewHookCandidate.kind`（schema/struct）→
   arbiter 内部 `PendingCandidate.kind` → `createCanonicalHook`/
   `create_canonical_hook` 落到新 HookRecord；未知 upsert 转候选时保留 kind。
4. **归并语义双端**：reducer `mergeHookRecord`/`merge_hook_record` 与
   arbiter `merge_candidate_into_existing_hook`——**kind 新值赢，缺席保持
   既有**（incoming.kind ?? existing.kind / .or()，零迁移兼容）。
5. **markdown 台账第 14 列双端往返**：`story/markdown` hook 表尾加
   「分类/kind」列（14 列形态；存量 13 列解析 kind=None 零迁移）；
   parse 经别名表归一（词表外文本 → None 不臆测）；render 尾列输出规范 id
   （无 kind 空单元格）。TS `StoredHook` 接口加 `kind?`；**往返闭环行为
   测试**（14 列解析 → 渲染 → 再解析 kind 保持；13 列旧行 kind undefined）。
6. **architect 种子钩子双端**：建书种子从自由 type 文本经别名表归一化
   kind（悬念/mystery → suspense 等；查不到则无 kind）——**零提示词
   变更**，存量种子表升级建书即刻获得分类。
7. **sqlite 投影不落 kind**（358 号先例）：MemoryDB hooks 表 8 列不变，
   kind 的持久化真相源 = markdown 台账（真相源单点，投影重建自动跟随）。

## 语义决策记录

- **schema 严格、边界宽容**：HookKindSchema 严格枚举保存储洁净；LLM
  手误在解析边界被归一/删除——两层职责分明。

## 教训

- **跨语言提示词镜像的机械验证该脚本化**：format!/模板字符串转义差异
  （{{ }}、\\"、\\u{201c}、\`）使肉眼比对不可靠——本次 Python 比对器
  归一化转义后逐行 diff 才算数（4 处伪差 0 实差）。
- 双类型体系（TS StoredHook ↔ HookRecord、Rust 同款）的持久化字段
  必须逐层核对消费方：markdown parse 产 StoredHook（TS）而 Rust 直接
  产 HookRecord——kind 往返要在**各自**类型上加字段，DB 投影层刻意不加。
- Bash 单命令 10 分钟上限下跑 criterion：负载门刚过的窗口里满采样会
  超时（PerfPowerServices 干扰使采样变慢约 2 倍）——`--sample-size`
  透传是脚本预留的正确逃生口。
