# 392 号：R22 反AI规则种子包——冷启动底线防线（四轮 P1 首件）

- 日期：2026-09-13

- 前序：[391 号 R21](./391_ContextLens上下文透视.md)、规划 [388 号 v4](./388_四轮规划立项.md)

## 做了什么

1. **契约批（rule-experience-engine 双端扩展）**：
   - `ANTI_AI_RULE_SEEDS`/`anti_ai_rule_seeds()`：内置 9 条种子规则，双端
     逐字镜像。取精弃糟：只收最高频、可机检、有明确改法的 AI 腔
     （眼中闪过一丝/值得注意的是/嘴角勾起一抹/空气仿佛凝固/深吸一口气/
     从某种意义上/瞳孔骤缩/不知过了多久/仿佛在诉说），覆盖全部四类型
     （phrase×3/structure×2/rhythm×2/cliche×2）；severity critical×2
     warning×5 info×2；全部字面匹配（正则种子留用户自建——误伤面不可控）；
     每条带双语场景的 zh 告警文案与多数带建议改法。
   - `antiAiRuleCanonicalForm`/`anti_ai_rule_canonical_form`：规则指纹
     canonical 形式（id|type|pattern|isRegex|severity|message|replacement|enabled
     以 | 连接，与 362 同编码约定）；`antiAiRuleContentHash`（FNV-1a hex16，
     对齐 362/360）；`antiAiRulePackHash`：逐条 canonical 以 \n 连接的组指纹
     （种子包完整性锚点）。Rust 侧 `AntiAiSeverity::severity_str` 改 pub。
   - `resolveAntiAiRulesWithSeeds`：种子兜底解析——文件缺失/损坏（undefined）
     → 种子内存态兜底（seeded=true，不落盘）；**文件存在但空规则 = 用户
     显式清空，不回填**（否则用户永远无法关掉防线，363 先例上明确的关键语义）。
2. **共享 golden（第 29 守门域扩展）**：`rule-experience-vectors.json` 追加
   四节——`seeds`（count/ids/typesCovered/packHash=32ba0a295a7dc436）、
   `seedCanonical`（逐字 canonical 锁）、`seedHash`（内容指纹）、
   `seedFallback`（缺失→种子/显式空不回填/自定义透传）。种子字面量三方
   镜像（Python×TS×Rust），packHash 由 Python 独立计算——任一侧改动
   种子即差分失败。TS +4 断言块（9 测试全绿）、Rust +3 测试（8 全绿）。
3. **接线批（四生产读取点 + 端点 + UI）**：
   - composer 双端：`loadRuleExperienceEntries`/`load_rule_experience_entries`
     接入兜底——缺失时注入种子 guidance 条目（source=rules/anti-ai 不变，
     **seeded 时 reason="Built-in anti-AI baseline rules (seeded)."** 供
     Context Lens 透传可辨）；显式空规则零条目。
   - detection 双端：TS runner 反AI扫描 + Rust write_next 反AI扫描同语义
     接入——冷启动书的审查自动获得 9 条底线扫描。
   - GET 端点双端：响应增 `seeded` 字段（TS server.ts/Rust ops_routes）；
     缺失→`{rules: 种子, seeded:true}`；显式空→`{rules:[], seeded:false}`。
     PUT 语义不变（保存即固化，种子随保存落盘）。
   - UI：AntiAiAndExperiencePanel seeded 徽标（「内置种子（未落盘，保存后
     生效为本书规则）」），任何 PUT 后转 false。
   - 行为测试双端各一组（缺失→种子条目/显式空→关闭）：TS
     `anti-ai-seed-wiring.test.ts` 2 用例 + Rust composer 测试 1 用例。
4. **基线修复**：Rust `compose_injects_reference_context` 断言更新——种子
   兜底后无规则文件的书在 G2 排序下 rules/anti-ai（style-asset=20）垫底，
   原断言「参考条目 .last()」改为「rules/anti-ai 垫底 + 参考条目 find」。

## 语义决策记录

- **种子是内存态不落盘**（363 铁律）：用户文件只在显式 PUT 时创建；
  GET 看到的种子不写盘。
- **显式空 = 关闭防线**：`{"rules":[]}` 不回填种子——用户必须保留彻底
  关闭反AI保护的权利；这是种子兜底与强制注入的分界线。
- **冷启动存量书即刻获得保护**：所有未配置规则的书（文件缺失态）在
  写作预防与审查扫描两面自动获得 9 条底线——这是本批的产品价值本体。

## 教训

- **366 号暗坑第二次咬人**：studio server.test.ts 的 core mock 显式
  白名单——本批新测试先后抓出 `ANTI_AI_RULE_SEEDS` 与
  `validateAntiAiRule`（366 号 PUT 路径就依赖它却从未入白名单）缺透传。
  该白名单是「按需透传」模式，新端点依赖的 core 导出必须逐个核对。
- 改嵌套 if-let 为 `and_then` 链时，旧代码的闭合括号必须逐层清点
  （composer/write_next 两处各余一个 `}`，编译前肉眼复查抓出）。
- Python 生成器对 zod `.optional()` 字段禁写显式 `null`（键省略才等价
  undefined）——`replacement: null` 被 zod 拒绝，生成器需幂等重跑能力。
