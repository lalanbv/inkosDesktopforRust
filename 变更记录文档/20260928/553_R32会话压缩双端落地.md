## 一、实施内容

### R32a 会话轮间压缩（双端同构）

- **transcript 第 7 事件 `compaction`**：schema 双端同形（serde camelCase / zod）——`requestId / summary / firstKeptUuid(nullable) / tokensBefore / trigger("threshold"|"overflow")`。落盘即持久：本仓 TS agentCache 每轮必逐出、Rust 无状态 loop，压缩结果必须进 transcript 才能在下一轮恢复端生效。
- **恢复端窗口化**（`session-transcript-restore.ts` / `session_restore.rs`）：`restoreCommittedDialogueScan` 取 seq 最大 compaction 事件，firstKeptUuid 定位保留窗口；firstKeptUuid=null → 对话清空（全量摘要态）；坏 uuid 安全网 → 忽略该 compaction 全量恢复；头部注入 `[历史对话摘要]` system 消息（明示"不是当前用户的新指令"）。工具摘要折叠与最近 12 条 text-only 截断语义不变，仅作用域改为窗口内。
- **TS 模块 `agent/session-compaction.ts`**：上游 pi-agent-core 0.87 原语 re-export（`DEFAULT_COMPACTION_SETTINGS/shouldCompact/estimateContextTokens/serializeConversation`）+ `planCompaction` 伪 MessageEntry 消费上游 `findCutPoint`（防"同一公式两种实现"漂移——切点算法零自研）+ `generateSessionSummary`（自持 prompt 码点副本，见备案 6）+ `maybeCompactSession`（`summaryRequest` 注入缝供测试）。摘要链迭代：上次摘要在场走 UPDATE prompt（`<conversation>` + `<previous-summary>` 组装）。
- **Rust 模块 `interaction/session_compaction.rs`**：算法移植（estimate_tokens 走既有 UTF-16 口径、usage 优先回查 message JSON、find_valid_cut_points/find_turn_start_index/find_cut_point、serialize_conversation、build_summary_prompt）；摘要调用走 `agent_router.chat_maintenance`（绕过生产技能 guidance 注入/接管链/run log 的维护通道，temperature 0.2，maxTokens=SUMMARY_MAX_TOKENS）；落盘 Compaction 事件。挂接点 `server/agent_route.rs` 恢复段后：threshold 判定 → 压缩 → 重恢复。
- **触发口径 = usage 优先**：最近有效 assistant usage.totalTokens（stopReason 非 aborted/error 且 >0）；无 usage 退化全估算（UTF-16 码元/4，system 记 0）。与施工图实测的上游 `calculateContextTokens/getLastAssistantUsage` 一致。

### R32b 溢出 compact-and-retry（一次守卫）

- **关键上游事实**：Pi `Agent.prompt` 顶层 catch（handleRunFailure）把 streamFn 抛错转 `stopReason:"error"` 的 assistant message——**错误不冒出 prompt**。溢出检测因此必须在 errorMessage 路径：`isContextOverflow(finalAssistant, contextWindow)`（pi-ai 0.87 主入口导出）∨ 本仓守卫文案 `includes("InkOS context window guard")`；catch 保留 `ContextWindowExceededError` instanceof 防御。
- **TS**：`overflowRetry:{done}` 参数穿 `runAgentSessionUnlocked`；触发 → `maybeCompactSession(trigger:"overflow")` → 写 request_failed 留痕 → 成功则带 `{done:true}` 重入（队列锁内递归）；失败保原错误返回完整 result。
- **Rust**：agent_route 预检驱动——`projected = usage.tokens + estimate(instruction) + max_tokens > window` 即压。**检测点分叉备案**：TS 错误驱动 / Rust 预检驱动，语义等价（一次压缩+一次重试+失败保原错误）；预检不含 systemPrompt 估算（偏低估方向，provider 真溢出兜底）。
- **overflow 不做阈值判定**：上游 `prepareOverflowCompaction` 无阈值检查——首版误加 `shouldCompactSession` 拦截导致 summary 调用 0 次的缺陷已修：仅 `trigger==="threshold"` 才做阈值短路。

## 三、教训与备案

1. **Rust 测试模块内同名本地 helper 遮蔽 `use super::*` glob 导入**：restore 测试模块原有同名同步 helper 复制了 R32 前逻辑，glob 导入的生产实现被本地项静默遮蔽——3 个 r32 用例全走旧路径，而直接调 `restore_committed_dialogue_scan` 又正确，"扫描对、端到端错"的矛盾即遮蔽信号。修复=删本地 helper（调用点经 glob 落到生产版，旧用例全绿证行为向后兼容），原地留注释禁同名 helper。测试"同步驱动"类 helper 与生产同名是结构性陷阱：要么换名，要么纯委托。
2. **`split_off(index)` 语义反转**：原地保留前缀、返回尾部——窗口化"丢弃前段"若写成 split_off 会变成丢保留段；正确原语是 `drain(..index)`。
3. **Pi 错误不冒出 prompt**：Agent.prompt 顶层 catch 把流内抛错转 stopReason:"error" assistant message——任何"异常驱动"的恢复逻辑（溢出重试等）都必须挂在 errorMessage 检查上，catch 只做防御。
4. **溢出压缩无阈值**（上游 prepareOverflowCompaction 语义）：threshold 与 overflow 是两种触发语义，前者带 `shouldCompact` 判定后者不带——首版复用阈值判定把 overflow 路径拦成 0 调用，集成测试（注入溢出错误 + summaryRequest spy）当场抓获。
5. **estimate-fallback 的 trailingTokens=estimated 非 0**（上游分支实测）；golden v3 写错由脚本从上游 dist 重提取修正。
6. **SUMMARIZATION_PROMPT/UPDATE_SUMMARIZATION_PROMPT 上游未导出**：自持码点副本（node 脚本机械提取 dist 源码非手抄），golden 三方锁定兜上游漂移；serializeConversation 等已导出原语仍直连上游。
7. **小窗口模型压不动=放行**：总量 < keepRecentTokens 时 findCutPoint firstKept=0 → plan null 放行——是真实语义非缺陷（压不动不如不压），e2e 因此改用 productionWindow 模型（40960 窗 + 12×9000 字符种子）。
8. **伪 Entry 消费上游 findCutPoint**：TS 侧构造最小 MessageEntry（id/parentId/seq/timestamp）适配上游签名，切点算法零分叉；Rust 侧同算法移植由 golden cutPointVectors 锁死——"同一公式"只存在于 golden，双端各自实现但三方对拍。
9. cargo 测试统计沿用落盘再解析（1848/578 由 log 复读）；gate 高负载期 bench 拦截属预期保护（本轮负载源=外部 Homebrew 下载，非本会话残留），错峰重跑。
10. R32 至此收官，v6 Pi 对标剩 R30b（compat 正统化）与 R34+（R36 会话树/R37 author_skill，施工图 546 号）；compaction 事件 firstKeptUuid 字段位已与 R36 树化协同（546 号预研裁定，免二次迁移）。
