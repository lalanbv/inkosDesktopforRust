## 实测考古（三段）

环境：fixture root **配置完整**（inkos.json custom:Mock 服务+secrets 有 key）+ Node 回退端+mock。

1. 前端：新会话发消息 → action.ts:498 硬拦「请先选择一个模型」（引 575 置顶表单）。
2. 后端直发（curl 不带 model 字段）→ **不以「未配置」拒绝**，进入解析链后报 `AGENT_LLM_ERROR: No API key for provider: openai`（pi-ai 库内部抛出）。
3. 矛盾点：secrets 有可用 custom:Mock key，错误却指向毫不相干的 `openai` provider。

## 定性

- Node 回退端 `/agent` 模型解析链在零显式模型时构造 **openai 系默认 pi Model 卡**，且 **secrets 服务配置未参与解析**——与 Rust 端四层解析（97 号）不同构；
- 因此前端硬拦**事实上有理**（零配置时后端不能兜底，575 置顶引导优于晦涩错误）——574 备案的「不擅动」裁决被实测**支持**；
- 真实缺陷重新定性：**配置了 custom 服务+key 的用户直发得到误导性错误**（配置在场被解析链无视）。

## 选项与建议（提案正文）

A 维持现状（零成本，绕过前端的调用方仍见误导错误）；B Node 解析链补 secrets 兜底（对齐 Rust 四层，触及解析链装配可挂 R45 seam 载体，需先裁决「静默兜底」产品意图）；C 最小错误面修复（secrets 有可用服务时错误消息改写为指认真实配置）。**建议 C 先行 + B 挂 R45 评估**。
