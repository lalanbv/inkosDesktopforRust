## 一、缺口分析结论

推送核验：origin/develop 仍停在 173 号（37958463），本地领先 22 提交，推送仍待用户在 Fork 操作；两项默认值未见用户答复，维持现状。

本轮聚焦 **doctor/诊断面 × 写作管线可靠性**：

1. **doctor 只查项目级**（inkos.json / .env / booksDir / LLM 探针 5+1 项），书籍级健康为零覆盖。
2. **最高价值缺口：最新章 state-degraded 会直接阻塞下一章写作**（`write_next::assert_no_pending_state_repair` → `PendingStateRepair` 错误，188 号用户报告的「后台任务失败」近亲），但诊断页对此**零预警**——用户只能在写作失败后才从报错知道。
3. `load_chapter_index` 自带磁盘重建自愈（索引损坏/缺失会静默重建），因此「索引损坏」类检查无检测价值（自愈后不可观测、且不阻塞）——分析后**有意排除**。
4. 其余管线失败模式（LLM 空响应→重试、审稿格式异常降级保存）已有处理面（174/188 号），无需诊断预警。

## 二、本批变更（改进项）

### 引擎（engine-rs，ops_routes.rs）

1. `get_doctor` 响应新增 **`bookIssues`** 数组（结构化，文案由客户端组装保证双语）：逐书 `load_chapter_index` → 最新章 `status == StateDegraded` → `{bookId, title, kind: "state-degraded", chapter}`。单书失败不影响整体诊断。
2. **测试**（+2）：降级最新章 → 恰好 1 条 issue（bookId/kind/chapter/title 全对）；健康书 → 0 条。axum oneshot 真路由（127.0.0.1:9 探针瞬间拒绝，不拖 9s 预算）。

### Node 回退端（server.ts）

3. doctor handler 同步 `bookIssues` 计算（语义与 Rust 对齐：最新章 status === "state-degraded"）。

### Studio（DoctorView）

4. 检查列表新增**「书籍健康」区块**：无问题 → 绿色「无写作阻塞问题」；有问题 → 琥珀色预警行（书名 + `doctor.issueStateDegraded` 文案含章号与修复指引「在书籍页点『修复状态』或重写该章」）。`bookIssues` 可选字段——旧后端缺省时按无问题渲染（向后兼容）。
5. **i18n**（+3 键，zh/en）：`doctor.bookHealth` / `doctor.bookHealthOk` / `doctor.issueStateDegraded`（`{chapter}` 占位）。
