## 二、实施

### Rust（engine）

- 新增 `utils/log_file.rs`：`append_log_event(root, level, tag, message)`——`{root}/inkos.log` JSON 行追加（字段对齐 Node `LogEntry`：timestamp/level/tag/message）；目录自建、失败静默（日志不阻断业务）、错误走 eprintln。单测 1（两行落盘 + get_logs 可解析形态）。
- **刻意不走 tracing 文件订阅**：lib 被 Tauri 壳嵌入时全局 subscriber 会与壳层订阅冲突；任务级事件直写是最小安全面。
- 接线三点（`agent_production.rs`）：连写章间失败（error，含 209 摘要文本）、连写中止（warn）、单章失败（error）。

### Node（core + studio）

- `utils/logger.ts` 新增 `createFileSink(path)`：appendFileSync JSON 行（同 LogEntry 形态）、mkdir -p、失败静默；导出进 `index.ts`。
- `server.ts` 组装处挂载：logger sinks = SSE + console + **fileSink(root/inkos.log)**——studio server 全量日志落盘（含 pipeline logger 面）。
- 测试 +2（logger-file-sink.test.ts）：JSON 行形态断言、写失败静默不抛。

## 四、结论与遗留

日志读写通道双端闭环：任务级失败（含连写部分完成摘要）持久可见，重启后可诊断。遗留：①Rust 管线细粒度 warn（tracing）仍只在有 subscriber 的宿主（Tauri 壳 stdout）可见——lib 层不加全局订阅是刻意的（壳冲突），任务级面已够诊断；②Node 侧全量落盘 vs Rust 任务级——形态不对齐可接受（诊断面，双端都有关键事件）；③`get_logs` 无轮转/上限（append 无限增长）——backlog：简单上限轮转（>N 行截头）。
