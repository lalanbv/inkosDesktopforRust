## 一、缺口分析（稳定性审计第二轮）

1. **`story/runtime/` 无限累积**：每章写 `chapter-{n}.run.json` / `trace.json` / `context.json` / `rule-stack.yaml` 四类观测工件（trace 含完整 LLM 交互轨迹，单章可达百 KB 级）。桌面常驻进程 + 长书（数百章）→ 数 GB 级缓慢增长，**无任何保留策略**（Rust 与 Node 双端皆然）。
2. `plan.md` / `intent.md` 为治理产物，体积小、可回溯——**保留**。
3. Box::leak 静态端口（每次 write-next 装配泄漏 ~10 个小分配）：每次 ~1KB 量级，相对写作时长可忽略；重构需端口生命周期改造，**记录为已知权衡**，不实施。

## 二、本批变更

### 引擎（engine-rs）

1. **`production/mod.rs`** 新增：
   - `runtime_retention_chapters()`：每书保留章数，默认 **20**，env `INKOS_RUNTIME_RETENTION_CHAPTERS` 覆盖（0 = 关闭清理，完全兼容旧行为）；
   - `prune_runtime_artifacts(book_dir, latest_chapter, keep)`：只清理 `story/runtime/` 下四类观测工件（run/trace/context/rule-stack）中章号 ≤ `latest - keep` 的文件；逐文件失败忽略（事后打扫不报错）。
2. **管线接线**：`write_next` 主流程 6b-2 步（节拍沉淀前）调用；`keep=0` 语义关闭。
3. **测试**（+2）：5 章 → keep=2 只留最近 2 章观测工件且治理产物全保留；keep=0 / 未超窗口为无操作。

### Node 回退端（core）

4. **`production/harness.ts`** 同语义 `runtimeRetentionChapters()` / `pruneRuntimeArtifacts()`（同一 env 名、同一四类后缀、同一治理产物保留）。
5. **`pipeline/runner.ts`** 接线：成功路径末尾（191 号节拍钩子前）调用，`.catch(() => undefined)`。
6. **测试**（`production-harness.test.ts` +2）：保留/清理矩阵 + noop 与默认值 20。
