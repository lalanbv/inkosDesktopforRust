## ① 两条红对跑的定性

**`strangler_session_domain_duel`（聊天回合后双端读面不等价）= 产品引擎腿真实缺陷。**

跨腿活体取证（Node 腿写一轮 → 产品引擎读同一份 transcript，修复前实录）：


根因：上游 2.0 的 `finish_turn` 收尾协议下，工具调用与结果都是 `visibility:"model"`，作者可见答复在收尾消息的 `display.completion.message`，正文 `content:[]`。产品引擎的读面投影只认 `display.thinking / toolExecutions`，把空收尾消息当「只闭合模型轮」跳过。Git 考古：投影移植于 2026-08-15（1.x 形态），上游 2026-09-25 才加 `display.completion / userInput` → 忠实移植 + 上游后改 = 漂移，产品引擎跟上，fork 自有增强（R36 active 链、sub_agent 标签、play_* 独立卡）保留。

## ③ Node 回退腿：R36 分支树语义缺失

活体双腿对照（同一套步骤）：Node 腿分支回第一轮后，读面仍含「第二问」，分支上新聊一轮读面是「第一问 / 第二问 / 新问」，**第三轮模型上下文仍收到弃用的「第二问」**；产品引擎腿读面与模型上下文都只含 active 链。

三处成因（692 号重施只回座了分支端点与 `/branches` 读面）：

1. `deriveBookSessionFromTranscript` 用全量事件投影消息；
2. `restoreAgentMessagesFromTranscript` 的对话回放扫全量；
3. 缓存 Agent 的有效性指纹只看「全量最大 `request_committed` seq」——分支只追加 `branch_moved`，指纹不变，缓存 Agent 的内存上下文原样带着弃用轮次进入后续模型请求。

修：①② 改按 `activeChainEvents`（元数据保持全局折叠）；③ 指纹改取 active 链上最后一个提交的 seq。中断工具交换也按链剪除——分支即作者把对话回退到该点，弃用分支上的半轮连其用户输入一并剪掉。纯 legacy 文件（无 `branch_moved`）过滤退化为全量，零行为变更。

**一个被变异否决的设计**：指纹最初是「链上最后提交 seq + 累计分支次数」二元组，理由是防「失败轮之后分支回上一个提交点」时内存残留半轮。变异（去掉分支次数分量）存活——单进程流程里它不可观测：失败轮本就逐出缓存，没有分支时照样污染，靠分支兜底不是对的修法。不可观测的代码不留，分量删除；那个残留隐患另立案（见 ⑫）。

测试：core 新增 `session-active-chain` 4 测（分支后读面与回放、弃用分支上的中断回合、resetLeaf、legacy 文件）；studio 新增路由级 1 测（mock 模型记录第三轮请求：含第一轮与分支新问、不含第二问；重载后读面一致）。活体复验（重建 core dist 后）：分支后读面「第一问 / OK」，第三轮模型上下文为「第一问 → 历史记录 → 新问」。

## ⑧ 双腿浏览器走查与走查发现

**Node 回退腿**：对话分支切换（两段式确认 → 只剩第一轮；分支上新聊接在其后；重载后一致；切换器标注「当前 / 已弃用分支」）、提示词面板（保存 ×2 → 回滚 → 恢复 builtin → 回滚到 `restore` 行得到完整内容而非空覆盖）、预算确认门（超预算被拦、「仍要发送」放行一次、下一条再次被拦、「取消」不放行且保留输入、告警条本轮结束即刷新）。

**产品引擎腿**：读 Node 腿写的会话三轮回复齐全（修复前只有 user 消息）；确认门与提示词回滚同过。

**走查发现（产品引擎腿真实缺陷）**：只想设个日预算，`PUT /services/config` 之后 `custom:Mock` 变成 `{dailyTokenBudget:1, name:"Mock", service:"custom"}`——**`baseUrl` 被抹掉了**。连带预算读面按端点主机匹配账本行，端点没了 → 恒 0 → 确认门永不触发。根因是 `merge_service_config` 同键整条替换，而 TS 是字段级合并（`{...previous, ...update}`）；产品引擎也没有 TS 的「`temperature: null` = 恢复默认」处理，此前靠整条替换碰巧丢掉 temperature。界面路径上同样会踩：服务页保存的表单不带预算与 maxTokens 键 → 抹掉手工配置的预算。

修：字段级合并（更新条目里出现的键覆盖、没出现的保留），并保住两个「出现即生效」的语义——`temperature: null` 删条目温度、被重置的是选中服务时顶层镜像一并删；`models: []` 清空清单（归一会把空值折成 None，须与「没带」区分）。

对跑级变异在这里抓到观测面选错：最初用 `GET /project` 判「顶层温度已删」，关掉删除后对跑仍绿（读面会按选中服务重新推导温度）。改为**每条腿 PUT 后立刻读盘上的 `inkos.json`**，此后变异被咬住。

## ⑬ 跟进：会话读面的量化与分配清理（高性能 / 0GC）

上面 ② 的「动作段用 `Cow` 借切片，不多复制一份」只是算法层面的论证——这条路径（每次打开会话、列会话、每轮聊天的缓存指纹）不在基准套件里，没有数字。补基准后才发现论证漏掉了大头。

**基准**：`session_read_face/project/200_turns`（`benches/hot_paths.rs`）。夹具 = 200 轮混合回合的 transcript（1133 个事件：纯文本 / 工具调用 / 2.0 收尾协议轮转，含一段已弃用分支），测「active 链过滤 → 已提交过滤 → 消息投影」。基准里带一个**布防时才计数**的全局分配探针（未布防时每次分配只多一次 Relaxed 原子读，同文件其余 32 项的测量条件不受影响——同一次门禁运行里它们的偏移都在 ±8% 内）。

| 200 轮会话投影一次 | 清理前 | 清理后 | 变化 |
|---|---|---|---|
| 分配次数 | 21,553 | 5,416 | −75% |
| 分配字节 | 2.90 MB | 1.00 MB | −66% |
| 耗时 | ≈515 µs | ≈208 µs | −60% |

分解（清理前）：整条 active 链深克隆 12,847 次 / 1.56 MB（六成），已提交过滤 24 次，消息投影 8,682 次。

**清掉的四处「只为喂函数而复制」**（行为不变）：

1. `committed_message_events` 收自有切片，而 `active_chain_events` 产出引用向量——读面与模型回放都先把整条链深克隆一遍。改为直接收引用切片。
2. 模型回放扫描里的 `windowed_events` 同样克隆整条链；`(消息, uuid)` 先成对再逐条克隆消息。改为引用向量与 `unzip`。
3. 工具卡挂到助手消息上时深克隆两份（`pending.clone()` 一份、`json!` 再一份）。改为移入。
4. 调用配对表每条调用复制四个 String（键两个、行两个），`use_skill` 请求集合也存 String。改为借用事件里的串。

剩下的 5,379 次是输出构造本身（每条消息约 13 次：对象节点、键名、正文、工具卡），已是 `Value` 型输出的下限附近；再往下要换输出类型，属设计决策。

**分配预算锁**：同一输入的分配次数是确定的（每次都是 5,416），预算卡在 5,500——每条消息多一次字符串复制（+398）即越线。基准里的断言 panic 会让 `cargo bench` 以 101 退出（bench 门禁与测试门禁都会红；后者经 bench 目标的测试模式也执行了一次）。必红自证：往库里放回一处工具卡克隆 → 7,661 > 5,500，越线退出。

基线手工登记新键（`benchesCount` 32 → 33，其余 32 项的值一字未动）；bench 门禁确认跑：33 项全过，最大回退 +7.9%（敏感词扫描，本轮未触）。

## ⑭ 流程踩坑

- **探针孤儿给出假结论**：探针结尾只杀了 tsx 的 CLI 包装进程，真正监听的子进程存活；下一轮探针的新进程抢不到端口悄悄退出，探活却对着旧进程（旧代码）成功，得出「修复无效」。处置：子进程独立进程组、整组击杀、探活循环发现子进程已退出立即判负。
- **变异测试两次抓到我自己的问题**：冗余修复（合并收尾）与不可观测代码（分支次数分量）。对跑级变异抓到观测面选错。
- `npx tsc` 从 `packages/` 目录解析到同名的无关包，退出码 0 是假信号 → 走各包自己的 typecheck 脚本。
- 对 `gate-ts.mjs` 用 `--help` 并接 `head`，脚本不认该参数直接开跑完整门禁（万幸未留进程）→ 门禁命令不接 `head`。
- 走查夹具启动时会重写 `inkos.json`：上一条腿设的预算被覆盖，差点误判成「引擎丢配置」。
- 一次 Edit 手滑把探针代码写进了生产文件，立即撤净并做残留扫描。
- zsh 通配零匹配中断整条命令 → 清理用 `find -delete` 或逐个列出真实路径。
- **「论证」不等于「量化」**：② 里凭算法写的「每事件 O(1) 次小分配」漏掉了整条链的深克隆（占六成）。凡是拿分配 / 性能说事的地方，先有基准数字再下结论。
- 夹具自检先于测量：基准夹具第一版漏了消息事件的 `uuid`，读边界对这种行是静默丢弃的——1133 行只读出 667。没有夹具自检断言，这个基准会测在一个空了大半的输入上并给出好看的数字。
- 基准夹具第一版用闭包同时可变借用 `seq` / `parent` / `lines`，循环体里又要读它们，借用检查过不了 → 改成显式构建器结构体。
- `clippy --all-targets` 会检查 bench 目标：`Vec<(&str, Value)>` 里写 `("key".into(), …)` 是多余转换（52 条）；rustfmt 把长条目拆成两行后，按键值形态做的批量替换会漏掉「键单独成行」的那些——改完要按 lint 输出逐条复核，别假设一次替换干净。
