## ① 守卫第二批：哪些面该守、哪些不该守

`router_books` 约 216 条路由。逐个读处理器的调用图（直接调用，以及经 `init_*` / `import_*_chain` / `run_radar*` 等辅助函数触达路由器），确认还有 **20 条**会调文本模型：

| 域 | 路由 |
|---|---|
| 章节工作区 | 灵感卡 |
| 文风 | 分析、导入、正典导入 ×2 |
| 衍生书 | 同人创建、刷新、番外创建、仿写创建 |

| 运维 | 雷达扫描、雷达分析、导演方向、定时任务启动 |

**明确不守**——错守等于把不需要文本模型的功能在未配置项目上一并拦死：

- 雷达榜单：只抓网页。

- 拆书、文风档案：纯启发式，零 LLM 引用。
- 互动叙事生图、影游节点图：走封面服务。

实现上加了一个 `guarded_post` 简写（POST 处理器 + 守卫 + 绑定状态），组合层 29 条统一写法。

## ② 产品路径缺陷（三处）

产品路径 = 桌面壳直接起引擎、不注入任何 `INKOS_LLM_*`，启动路由器恒为「未配置占位」（discard 端点）。

**（1）灵感卡、（2）确认动作「起草结构」绕过项目配置。** 两个处理器直接用 `runtime.router`（启动路由器），而其余模型面都走 `effective_router()` 热解析。结果是：**无论项目怎么配模型，这两个功能都连不上**。回归测试（占位启动路由器 + 项目配置指向进程内 mock）在修复前全红，错误信息正是占位端点 `http://127.0.0.1:9/chat/completions`。

**（3）界面显式选定的模型对确认动作不生效。** 这是核验上一条改动时发现的：`post_agent` 按用户选定的服务构造一个「覆盖路由器」，聊天轮直接用它；但确认动作（建书、写下一章、短篇……）的执行器一律经 `effective_router()` 取路由器——项目配置可用时它返回的是**项目默认**路由器。平时看不出，因为覆盖解析的第 2 层恰好等于项目默认；用户显式选了别的服务或模型才会暴露。端到端实证：项目配两个服务，请求里显式选第二个并触发「起草结构」——修复前**选定服务命中 0，动作却返回 200**，跑在默认服务上。

修法：请求级作用域（`tokio::task_local`）+ `with_request_router`，`post_agent` 在有覆盖时把确认动作放进作用域，`effective_router()` 在作用域内优先返回选定路由器。一处改对全部执行器，不动 `BooksRuntime` 的结构（它有上百处字面量构造）。

## ③ 确认动作错误面：对齐上游重构

git 考古：TS 在 b399a8d3（2026-08-30「replace legacy creative control paths」）改了 `formatAgentActionFailure`——非忙失败从 `502 AGENT_ACTION_FAILED` 改为 `500 INKOS_ACTION_ERROR` + 语言前缀，载荷缺失经 `ApiError` 原样透出为 `400 CONFIRMED_ACTION_PAYLOAD_INCOMPLETE`。Rust 端口是 2026-08-16 移植的，忠实搬的是**重构前**的形态，上游改后没跟。属于「忠实移植 + 上游后改」，Rust 向 TS 对齐。

| 类别 | 改前（Rust） | 改后（= TS） |
|---|---|---|
| 派发期载荷缺失（27 处） | 502 `AGENT_ACTION_FAILED` | 400 `CONFIRMED_ACTION_PAYLOAD_INCOMPLETE` |
| 意图不在执行表 | 502 `AGENT_ACTION_FAILED` | 400 `UNSUPPORTED_CONFIRMED_ACTION` |
| 执行失败 | 502 `AGENT_ACTION_FAILED` 原文 | 500 `INKOS_ACTION_ERROR` +「InkOS 动作失败：」 |
| 忙 | 409 `BOOK_BUSY` | 不变 |
| 用户主动中止 | 502 + 中性文案原文 | **刻意不变** |

中止面是 Rust 侧的增强（209 号，TS 无对应物），不随上游改：套上「动作失败」前缀会与「用户请求停止」自相矛盾。

## ④ 需要模型的确认动作：调用前检查

1669 号立案时写的是「逐意图分类未做」。这一轮读清了派发器，分类可以落实：12 个意图需要文本模型，4 个不走（生成封面走封面服务、翻译创建只建项目、连接选择与删除节点是纯结构操作），2 个不可确认。归类写成穷尽 `match`、不设通配——以后新增意图即编译红，逼出归类。

检查放在载荷校验之后、执行之前（与 TS 次序一致），收尾同 TS 对 `ApiError` 的处理。此前未配置时建书会一路跑进执行期、以不相干的 500 失败（突变实测：「Genre profile not found」）。

## ⑤ TS 侧：探针实跑打出一处双端不同码

给 TS 的对应面逐个实跑，15 个面里 9 个直接回 400，其余是我的探针载荷没过各自的入参校验。但有一条异常：**仿写创建回了 200**。读代码发现仿写 / 番外创建是即发即忘面——HTTP 立刻回 200「creating」，模型在后台任务里才调用，配置错误只能走 SSE。而 Rust 现在是组合层守卫同步 400。

TS 向 Rust 对齐：加前置检查，未配置同步回 400，不留一个注定失败的后台任务和「创建中」状态。

## 流程

并行会话的在途改动（5 个文件 + 1 个未跟踪脚本）里含我必须改的 `e2e_write_next_contract.rs`（它改的是 config56 模块里 `/project` 的 temperature 断言，我改的是另外 11 处断言，不同区域），所以实现全程在独立 worktree 做（`/tmp/wt1670`，基线 b8582483）。

**先行落地的判断与做法。** 20:17 复查：对方在途文件最后修改于 11:42，此后 8.5 小时零改动，机器上没有任何 cargo / vitest 进程（只剩它两枚孤儿 sidecar），主树 `cargo check --all-targets` 已能过——按「对方停摆」处置，不再无限等。落地的约束是对方工作副本里的在途 hunk 既不能丢、也不能在它之后被回退（路径限定提交取的是工作副本全量；它的工作副本若停在「旧基线 + 其改动」，下次提交就会整体回退我方）。做法：

1. 先把我在重叠文件里的 hunk 用 `git apply` 合进**对方的工作副本**（`--check` 先过）；
2. 分支快进到 worktree 提交（带旧值校验的 `git update-ref`）；
3. 12 个无重叠文件检出，重叠文件只对齐索引（不动工作副本）。

核对：落地提交的树哈希与 worktree 提交相同；索引 == HEAD；对方在重叠文件里的 hunk 落地前后逐行相同；其余在途文件与未跟踪脚本未被触碰。落地后对方的工作副本是「新基线 + 其改动」，它之后做路径限定提交不会回退我方。

**判断的时效。** 落地的同一分钟发现对方会话恢复了活动（`session_transcript.rs` 自 20:21 起又在被编辑）——「停摆」只在落地那一刻之前成立，幸运的是落地方式本身不依赖对方停摆：无论对方是否在编辑，它的在途 hunk 都被保住。残余风险只有一个：对方用落地前读到的整文件内容做整体覆写，那 11 处断言会回到钉旧 502 的形态——在新代码下必红，它自己的门禁会发现。
