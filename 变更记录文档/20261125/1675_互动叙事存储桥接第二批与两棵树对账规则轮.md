# 1675 号：互动叙事存储桥接第二批（Node 腿认得产品引擎创建的世界）+ 两棵树都在时的对账规则

> 日期：2026-11-25 ｜ 类型：存储桥接施工轮（两腿）+ 对账规则定线轮 + 对跑门禁棘轮
> 定位：1673 号追记给第二批留了一条施工输入——「Node 腿认得产品引擎创建的世界；动工前先定 legacy 根世界没有作品清单时，回合收尾的同步走哪条路」。本轮先把这条路取证清楚，据此给出「按需迁移到 works + 对账规则」的方案，再做风险最小的一批；上一轮钉下的「产品引擎创建 → Node 腿 404」翻成互读可见，两个方向的桥接至此都通了。

## ① 取证：legacy 根世界在 Node 腿上走不通的三处（先红）

产品引擎创建的世界只有 `worlds/<id>/` 一棵树。先写测试再修，修前实跑 4 红 1 绿：

- **发现不了**：`PlayStore.loadWorld` 回 null，`listWorlds` 不列——Node 腿按 works 清单发现世界。
- **读取面不认**：真实 Node 服务 `GET /api/v1/play/runs/<id>/main` 回 404（1672、1673 号钉下的现状）。即使迁移（拷贝）之后仍 404 `PLAY_RUN_NOT_FOUND`——读取面只认 `play.db`，产品引擎新建的运行是文件后端 `play-graph.json`。
- **回合收尾会失败**（本轮要定的那条路）：`syncWorkSourceArtifacts` 第一步 `loadWorkManifest` 直接 ENOENT。没有作品清单的世界即使被看见，回合也会在收尾同步处失败。

结论：**legacy 根世界必须先进 works（有清单）才能在 Node 腿上玩**。「Node 腿读取面直接回退读 legacy 根」这条路不成立。

## ② 方案：按需迁移到 works + 两棵树都在时的对账规则

候选与否决理由：

- **Node 腿读取面直接读 legacy 根（不迁移）**：①的第三处过不去；而且 Node 腿的写面只写 works，读写分根。
- **Node 腿也按「谁新用谁」选根**：回合必须在 works（清单、版本索引都在那里），写之前还是得把较新的那份拷进 works——等于迁移。
- **选定：首次触达按需迁移 + 对账规则。**

对账规则：**进度较新的那份为准，打平取 works。** 判据是「进度钟」——`world.json` 与各运行下 `transcript.jsonl`、`state/current.json`、`play-graph.json` 四类文件修改时间（整毫秒）的最大值。不含 sqlite 文件：库里有未检查点的帧时（写连接异常退出，或迁移把 WAL 一并拷了过来），读连接开、关一次就会做恢复与检查点，库文件的修改时间在「读」的时候变——本轮实测（写连接异常退出后，读连接开关使库文件修改时间变化、WAL 被收掉；没有待检查点的帧时纯读不改）。读一次就可能「变新」的文件当不了进度钟；回合每轮都写转录与状态，钟照样往前走。

| 状态 | 怎么来的 | 产品引擎 | Node 腿 |
|---|---|---|---|
| A 只有 legacy 根 | 产品引擎新建 | 用 legacy 根 | 首次触达时迁移 |
| B 两棵都在，works 较新 | Node 腿触达之后 | **换到 works** | 读写 works |
| C legacy 根较新 | 显式迁移之后用户接着在产品引擎上玩过（1675 号之前产品引擎对「两棵树都在」一律用 legacy 根） | 仍用 legacy 根 | 读得到落后副本，**拒绝续写** |

三个动作必须一起做，少一个都比不做更糟：

- **只做按需迁移、产品引擎不换根**：迁移之后产品引擎仍写 legacy 根，Node 腿第一次触达之后立刻再分叉——桥是空的。
- **产品引擎换根、Node 腿不拒写**：C 态世界在 Node 腿上一回合，works 就成了「较新的那份」，产品引擎跟着换到落后副本上，legacy 根里较新的进度被撂下——比现状更糟。
- 所以 C 态下 Node 腿拒写（`PLAY_WORLD_DIVERGED`，错误信息写明原因与出路）；两份的自动对账留到第三批。

## ③ 施工

**Node 腿**

- `PlayStore.loadWorld`：works 里没有、legacy 根有时调 `ensureWorldStorage`——复用 `migrateLegacyWorks({ apply: true, source })`（拷贝全部文件 + 建清单，原目录保留），再读一次。`listWorlds` 列之前对 legacy 根下还没进 works 的世界逐个按需迁移。
- `PlayDB` 构造：`play.db` 不存在时先读 `play-graph.json` 再开库，导入四张表；之后再开不重跑。**记录按列投影**（见下）；投影后仍不合 schema 就在开库之前抛 `PLAY_GRAPH_INVALID`——不留下缺记录的库，库一旦建出来产品引擎就改读它。
- 续写守卫：`ensureRun`（所有运行级写入的第一步）与 `updateWorld` 两处调 `assertNotBehindLegacy`。`createWorld` 对「legacy 根有同 id 的世界却没能带进 works（迁移判 invalid 或 conflict）」拒绝新建——新建的那份会变成较新的那份，产品引擎跟着换过来。
- `server.ts`：读取面认 `play-graph.json`（`playRunHasGraph`）；PUT image-settings 与 GET images 先迁移再取路径——对只在 legacy 根的世界直接往 `works/<id>/source` 写，会留下一份没有清单的孤儿目录，之后迁移判 conflict；generate-image 的「图谱在不在」同判。

**产品引擎**：`play::world_dir` 两棵树都在时按 `progress_clock` 选根，与 Node 腿的 `progressClock` 逐项对应。

**为什么导入必须按列投影**（读码取证四处）：产品引擎的文件图谱存的是模型输出的原样对象——

- `play_parser::backfill_edges` 只补规范键、不删别名键（`from`、`relation`…）；
- 模型多给的键原样留着；
- `apply_play_mutation` 的 `build_event` 给事件加 `timeAdvance`；
- `models/play.rs` 的 `PlayEdge.confidence: Option<f64>` 序列化出 `confidence: null`。

TS 的图谱 schema 全是 `.strict()`，整对象校验在真实世界上必然失败。产品引擎自己写 sqlite 时也只取这几列、`None` 存 NULL，导入照做：只取表里有的列，`null` 的可选键当缺省。

本机没有真实世界样本（桌面应用唯一登记的项目根是仓库自身，其下没有 `worlds/`、`works/`），所以对跑样本由产品引擎的生产写入函数现场生成（`normalize_play_mutation` → `apply_play_mutation` → 文件后端 `flush`），并断言样本确实带着别名键、多给的键、`timeAdvance`。手搓的干净样本证明不了导入。

两个存活变异（测试原先没咬住，已补强）：

- **「导入只跑一次」**原先只断言后来加的实体还在——重跑导入是 `INSERT OR REPLACE`，不会删它。改成断言导入之后改过的记录不被盖掉。
- **「打平放行」**原先把 legacy 的转录拨到 0，造出的是「legacy 更旧」而不是打平。改成把两棵树的进度文件钉到同一时刻。

## ⑤ 已知限制（如实）

- **C 态世界在 Node 腿上没有自动出路**：读得到落后副本，不能续写。两份的对账（旧份归档后并回）是第三批。
- **迁移是拷贝**：恰逢产品引擎写一轮时 works 那份可能撕裂（毫秒级窗口；原目录完整保留）。
- **进度钟不看图片、检查点这类非进度文件**：只有这些文件更新的分叉判不出来。
- legacy 根那份冻结不清理；显式迁移仍会拷贝。
- 界面层的互动回合走查没做（走查 mock 没有两腿 play 协议分支）；壳内走查没做。
