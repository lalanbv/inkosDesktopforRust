# 1680 号：聊天循环「未知工具守卫」两腿同口径轮

日期：2026-11-25。前置：1677 号（第十一节第 4 点的走查备案，已在该记录第十二节勘误）。起点是校验器把两条备案列为「已坐实未处理」：产品引擎聊天循环对未知工具打满重试、界面保存未每次打探测请求。复核结果：后一条是我归因错了；前一条暴露出 Node 腿的一个真问题。

编号说明：并行会话的 worktree 名为 `wt1679`（它的下一轮），本轮顺延取 1680。

## 一、取证（两腿真实服务进程 + 回环上游）

探针起两腿真实服务进程，配一个指向回环上游的自定义服务，上游记录**全部**请求（方法 + 路径 + 请求体是否带工具）。

| 场景 | Node 腿 | 产品引擎 |
|---|---|---|
| 界面保存前的 `POST /services/:id/test` | 每次打上游 `GET /v1/models`，200 `ok: true` | 同左 |
| 上游对所有请求都回工具调用（退化 mock） | **342 次** / 4.3 秒，502「Context compilation returned an unexpected tool call」 | 12 次 / 32 毫秒，200 |
| 逼真 mock：带工具的请求回一个不存在的工具，不带工具的（上下文压缩）回正文 | **20 秒 690 次**（688 + 2 次压缩），到 20 秒客户端主动断开；**断开后 3 秒内又打了 26 次** | 12 次 / 20 毫秒，200 |

读码对上的事实：

- `@mariozechner/pi-agent-core` 0.73.1 的循环（`agent-loop.js`）**没有任何轮次上限**。模型调了不存在的工具，循环只回一条 `Tool X not found` 然后继续问模型；唯一的出口是模型不再调工具、流出错或被中止。Node 腿每次模型调用强制 `toolChoice: "required"`，收尾全靠模型自己调 `finish_turn`。
- 上下文塞满不是出口：压缩成功后循环接着跑。
- 客户端断开也不是出口：聊天路由用的是服务端自己持有的控制器（`chatRequest.controller.signal`），另有显式的 `POST /sessions/:id/abort`——请求按设计是可持久、可重连的，这是既有设计，不算缺陷。但它意味着卡住的循环会一直烧到用户点停止。
- 产品引擎 `run_agent_loop` 有 `MAX_ROUNDS = 12`，打满后以空回复收场。有界，但对明显没戏的循环仍会盲打满。

## 二、定性与口径

**缺陷**：Node 腿的聊天循环无界。本地 mock 快，所以是「690 次 / 20 秒」；换成真实上游（每次几秒、上下文越来越长）就是无上限的时间和费用。

**口径（两腿同值）**：连续 **5** 轮「整轮只调了工具表里没有的工具」就停止。

- 为什么只认这一种：不存在的工具什么都不会执行，整轮都是它 = 定义上的零进展，收掉它不可能误伤任何正常流程。
- 为什么不泛化成「工具失败」或「总轮次上限」：
  - 工具适配层里抛错才是 pi 层的 `isError`，领域层的失败 / 被拦截结果是当正常文本返回的——按 `isError` 判会漏，还会误伤确认流程里被拦截的轮次。
  - Node 腿的合法流程能跑多少轮没有数据（长篇批写、后台任务都可能很长），产品引擎的 12 是它自己的既有约束。总轮次上限是产品决策，见第六节。
- 阈值 5：有能力的模型错 1–2 轮就改口；工具名是 `能力__动作` 这种长名字，弱模型可能要多试几次。留 5 轮容错，最坏情况也只浪费 5 次请求。

## 三、实现

两腿共用对照表 `packages/studio/src/__tests__/golden/agent-loop-guards.json`（`maxConsecutiveUnknownToolRounds: 5`），两腿测试各读一次——改这个数必须两腿一起改。

**Node 腿（`packages/core/src/agent/agent-session.ts`）**

- 计数挂在 `transformContext` 前面：pi 每轮模型调用前走它一次（先于 `streamFn`），拿到的消息尾部就是刚执行完的那一轮。尾部一串工具结果前面的助手消息是这轮的调用；整轮的名字都不在 `cached.agent.state.tools`（pi 查表用的同一张表）里 → 连续计数 +1 并记下工具名；只要夹着已知工具就归零。尾部不是工具结果收尾（开局）时不计不动。
- 停止走既有机制：连续轮数到上限后，`streamFn` 返回 `stopForWorkTransition`（与 `finish_turn` 收尾同一条路），回合按既有路径失败，`errorMessage` 是 `Agent stopped: the model called unknown tools ("no_such_tool") in 5 consecutive turns.`。工具名来自模型输出，截短并加引号转义后才进文案。
- 新增状态只有两个：连续轮数、最近未知轮的工具名。停止条件与错误文案都从轮数派生，没有预先写好的「原因」字段。

**产品引擎（`engine-rs/src/interaction/agent_loop.rs`）**

- 每轮统计调用数与「`Unknown tool`」结果数（复用既有 `is_error` 的判据）；整轮都是未知工具则连续计数 +1，到 5 就 `break`。结局与轮次上限相同（空回复 + 工具错误明细），对外形态不变，只是不再盲打满 12 轮。两个 `usize` 计数器，零新增分配。

## 四、验证

**回归测**

- Node 腿 `packages/core/src/__tests__/unknown-tool-loop.flow.test.ts`，5 条：到上限即停（请求数 = 5、错误文案、转录末事件 `request_failed`）／差一轮改口照常收尾／夹着已知工具的轮次归零／同名未知工具调两次算一个未知轮／上一个请求的未知轮不带到下一个请求。
- 产品引擎 `agent_loop.rs` 单测 2 条：连续未知轮在上限处停、不再打满 12 轮；夹着真实读取的混合轮归零、之后差一轮到上限照常收尾。
- 夹具是有界的：脚本用完还来请求就回 500。守卫被拿掉时用例很快以「请求数对不上」变红，而不是空转到超时。

Node 腿还有一个**存活变异**：「每次请求把计数归零」这一行删掉后没有任何用例变红。查实是代码冗余，不是测试没咬住——两条失败路径都会清掉缓存项；能被下一个请求复用的缓存项，上一个回合必然正常收尾，最后一轮是 `finish_turn` 或动作回放，那一轮已经归零。处理：删掉这行，把不变量写进字段注释。另做了一个判决性实验确认用例前提成立：把所有归零都拿掉，「请求之间不串账」那条变红，说明两个请求确实复用了同一个 Agent。

## 六、备案（未改）

1. **Node 腿仍然没有总轮次上限。** 本轮只收了「整轮只调不存在的工具」这一种。模型卡在已知工具上（反复失败、反复成功读同一个文件、未知与已知交替）时循环仍无界，要等用户点停止。要不要加总上限、上限多少，需要产品裁定：得先确定合法流程的最大轮数（长篇批写、后台任务）。产品引擎的 12 轮上限是它自己的既有约束，同样会把需要更多轮的合法流程截断成空回复。
2. **两腿对「回合没完成」的呈现不同。** 产品引擎是 200 + 空回复（界面「（无回复内容）」+ 工具错误卡片）；Node 腿是 502 + 原因文案。沿袭各自既有契约，本轮未动。
3. 阈值 5 是经验值，没有真实模型的卡住样本可以校准。要调就改对照表，两腿测试会逼着一起改。

## 七、教训

1. **库的包装类可能不转发钩子。** 第一版把守卫挂在 `shouldStopAfterTurn` 上——底层 `runAgentLoop` 的配置类型里有它，但我们用的 `Agent` 包装类转发配置是白名单，运行时被静默丢弃。类型检查当场就能报（`TS2353`），但我先写了代码直接跑测试，第 1 条用例空转到 20 秒超时才暴露。生产代码改完先跑 typecheck，这条之前记过，又踩了一次。
2. **探针的 mock 必须和被测协议同形。** 第二版探针把服务配成流式，mock 却回非流式 JSON，两腿各打 1–2 次就报「空响应」——差点把这当成结论。
3. **采集面不完整就会得出错误归因。** 「保存不打上游」是因为采集器只记了 `/chat/completions`。写「没有 X」之前先确认量具能看到 X。
4. **变异存活要分清是测试没咬住还是代码冗余。** 前者补用例，后者删代码；删之前得有判决性证据。
5. **自己复查出来的判定盲点要专门补用例。** 「同名未知工具调两次」的误判对已有 4 条用例都不敏感，只有专门为它写的那条能咬住。
6. **只杀 tsx 包装进程会留下监听子进程。** 第一版探针直接杀子进程，留下一个占口的 Node 服务；改成独立进程组后整组清干净。
7. **对方在主树跑门禁时不碰主树。** 本轮开头对方正在跑全链，等了约 20 分钟才起探针——探针用主树的源码和构建产物，抢跑既可能读到半成品，也会给它的测试腿加噪声。
