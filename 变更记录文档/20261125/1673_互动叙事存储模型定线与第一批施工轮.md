## ① PlayHud 取证：请求形态两腿都对，问题只在存储

1672 号的备忘里有一条猜测：「`PlayHud` 用会话 id 当世界 id 请求 `/play/runs`，这只在产品引擎上成立，在 Node 腿上表现未取证」。实跑与读码的结论是**猜测不成立**：

- **两腿都是「世界与会话 1:1 绑定，世界 id 即会话 id」**。TS 2.0 的 `play_start`：`worldId = safePlayId(sessionId, sessionId)`；产品引擎同义（`world_id = session_id.trim()`，注释写明 1:1 绑定）。
- **HUD 请求的是 `/play/runs/<playWorldId>/main`**，其中 `playWorldId = 会话绑定的作品 id ?? 会话 id`。Node 腿建「play」会话时会话自带 `profileId: interactive-world`、`workId` 即会话 id——两者相等。
- **Node 腿真实服务上的接口表现**：世界还没建 → `404 PLAY_WORLD_NOT_FOUND`（HUD 对 404 静默回落到空状态）；世界建好 → 200。
- **浏览器实跑（Node 腿）**：首页「其他创作」把这个世界列成 `interactive-world` 作品 → 作品页（标题、生成物 `source/world.json`）→「与 Agent 继续创作」→「查看世界」→ HUD 显示「1 幕 · TS 腿世界」「我面对的：雾港来客」。

所以 Node 腿上 HUD 不是一个独立问题；它看不到的只是**产品引擎创建的世界**——即 1672 号坐实的存储分叉，本轮第一批解决其中一个方向。

两条顺带观察（都不改）：

- 会话 id 超过 80 字符时两腿行为不同：TS 抛「Invalid play id」，产品引擎截断到 80（世界 id 就不等于会话 id 了）。实际会话 id 由时间戳加随机段生成，不会触发。
- 侧栏会话条目的相对时间按 **id 前缀**里的时间戳算：我手造的会话 id 前缀是 7 月的，显示成「4 个月」，而接口返回的 `createdAt` 是正确的。真实 id 前缀即创建时刻，不会出现落差。

## ② 定线方案：自动双向桥接，分三批

**取证给出的约束**：

1. TS 2.0 的 works 布局是上游契约（`PlayStore` 经 `workDirectory`；作品清单 `work.json` 加 `syncWorkSourceArtifacts`）。
2. 产品引擎既有的互动世界全在 `worlds/`——那是产品默认引擎的全部存量。
3. 两种布局下，run 与世界级文件的**相对路径相同**，换根即可互通。
4. 图谱库的表结构两腿只差一列（见 ③）。
5. 显式迁移 `migrateLegacyWorks` 是**拷贝**，会制造「两棵树都在」。
6. 书域（`books/` ↔ `works/<id>/source`）是同一个问题，1671 号把两条对跑留在了同一个前提上。

**两个候选**：

| | 方案 A：产品引擎迁到 works | 方案 B：自动双向桥接 |
|---|---|---|
| 做法 | 产品引擎新建世界写 `works/<id>/source`，并在 Rust 里生成维护 `work.json` 清单 | 两腿各按同一条规则解析世界的实际根，读写同根 |
| 存量 `worlds/` | 需要一次性迁移（搬走，或拷贝后优先 works） | 不动 |
| 新增的漂移面 | Rust 里多一份 2.0 作品清单协议的实现 | 一条共用的解析规则 |
| 可否分批 | 难，迁移与清单协议得一起上 | 可以，每批独立可发、可回退 |
| 收益 | 单一布局 | 每个世界只有一份活的拷贝 |

**选 B。** 理由：风险最小，与「产品引擎是默认引擎、Node 是回退」的现实一致，不需要在 Rust 里养第二份作品清单实现。A 的收益（单一布局）可以在 B 之后作为出口再做——届时只是把新建世界的默认根从 `worlds/` 改成 `works/`，桥接规则照旧保证存量可见。

**解析规则（两腿共用同一条）**：

1. `worlds/<id>` 是目录 → 用它。
2. 否则 `works/<id>/source` 里有 `world.json` → 用它。
3. 否则 → 各腿的默认根（产品引擎 `worlds/<id>`，Node 腿 `works/<id>/source`）。

**分批**：

- **第一批（本轮）**：产品引擎认得 Node 腿创建的世界，读写同根；图谱库表结构兼容。
- **第二批**：Node 腿认得产品引擎创建的世界。`PlayStore.worldDir` 加 legacy 根兜底（works 清单缺席而 `worlds/<id>/world.json` 在 → 用 `worlds/<id>`，读写同根）；`listWorlds` 纳入 legacy 根下的世界；图谱——Node 腿读取面认文件后端的运行，首次打开时把 `play-graph.json` 的四类记录导入新建的 `play.db`（一次性升级，之后两腿都走 sqlite）。
- **第三批**：收口「两棵树都在」。桥接之后不再需要第二份拷贝——迁移不再拷贝 `worlds`；已有的双份做一次对账（按修改时间取新，旧份归档）。
- **出口（可选）**：新建世界的默认根迁到 works。

## ③ 第一批施工

**根解析器**（`play::world_dir`，`run_dir` 随之）：按上面的规则解析。指令里举的例子是「读取面在 `worlds/<id>` 缺席时回退读 `works/<id>/source`」；实施时改成**读写都按同一个解析结果走**——只回退读面的话，产品引擎认出 Node 腿的世界后，下一回合会写进 `worlds/<id>`，同一个世界立刻分叉成两份。所有读写面都经这两个函数取路径（`play.rs` 内 20 处、外部 12 处），改这一处即全量生效；判定只做两次 stat；备份集本来就同时含 `works` 与 `worlds`。

**图谱库表结构兼容**。实施中发现的第二道坎：`edges.confidence` 这一列是 TS 1.x 的（2026-05 起），上游 2.0 在 2026-08-30 删掉了它；产品引擎是 2026-08-16 移植的，带着这一列。Node 腿建的 `play.db` 因此没有这一列，而：

- 只读快照照旧 `SELECT … confidence` 会在 `prepare` 处失败，**失败后的回退是文件后端 = 空图**——有数据的世界被静默显示成空的；
- 读写后端里凡带这一列的读写都会报「no such column」。

处理：只读快照不写库，改成按实际表结构选列（有这一列才选）；读写后端打开时补上这一列（`ALTER TABLE edges ADD COLUMN`，纯增量——Node 腿的 INSERT 不列它，读到也不认识，互不影响）。

**行为边界**（如实写明）：

- 产品引擎既有世界：`worlds/<id>` 在，行为不变。
- 两棵树都在（显式迁移留下的拷贝）：产品引擎仍用 `worlds/<id>`，既有用户的连续性不变；它与那份拷贝的分叉是既有状态，第三批处理。
- 产品引擎直接写 `works/<id>/source` 不会更新 `work.json` 的生成物索引（2.0 的「生成物与版本」）。读取面按目录读，不受影响；版本面在回到 Node 腿的下一次回合收尾时并进去，不冲突——取证过程见文末「追记」。

## 追记一：版本索引取证

正文原先把「产品引擎直接写 works 树与 2.0 生成物索引的关系」记成未取证。收尾后读码加实跑，把它坐实：

- **Node 腿的互动回合执行流会把每回合改动的源文件登记成作品清单里的当前版本**（`play-runner.ts`：回合前 `captureWorkSourceState`，回合后 `syncWorkSourceArtifacts({accept: true, acceptPaths: 改动的路径})`）。所以运行文件在 Node 腿上是进版本面的——正文 ③ 里「读取面按目录读，不受影响」只说对了一半：读取面确实不受影响，但版本面会滞后。
- **产品引擎直接写盘不登记**：在产品引擎上玩的回合，2.0 的「生成物与版本」看不到新版本，要等回到 Node 腿、下一次回合收尾的同步才并进去。这是第一批的已知落差，不是回归（2.0 作品页依赖的 works 接口只在 Node 腿上存活，产品引擎的界面不走那条路）。
- **并进去的时候不冲突**：同步里那个「Source changed before revision commit」守卫只在「带 `writes` 的同步且当前版本没有快照」时触发；回合收尾用的是 `acceptPaths`、从盘上读字节，不满足条件——它直接按盘上现在的内容建新版本，把旧的当前版本标成已被取代。

证据做成了对跑断言（`interactive_world_node_created_world_is_shared_duel`）：播种脚本的 `create` 末尾照真实的回合收尾做一次同步（`play.db`、转录、当前状态登记成当前版本，`play.db` 走 sqlite 备份快照）；产品引擎续写后断言清单里转录的校验和 **不等于** 盘上的 sha256（落差钉住）；再跑一次回合同步（脚本新增 `turn-sync`），断言不报错且校验和 **等于** 盘上的。过程中踩了一个自己的笔误（脚本里变量叫 `worldId`，同步调用里写成了 `workId`），两条对跑一起红在播种处——单独跑一遍脚本才看见。

还差一截没管：产品引擎改了、而 Node 腿下一回合没有碰到的文件（比如 `images/settings.json`），不会进那一回合的 `acceptPaths`，要等某次带 `writes` 的同步或非接受的同步才会被登记成候选版本。实际影响小（那些文件不是版本面的主体），记在这里。

## 追记二：`play_start` 对已存在的世界是更新，不是重建

收尾后回头核「第一批有没有漏掉的交互面」，核出一个真问题，而且是第一批把它的波及面扩大了的。

**问题**：产品引擎的 `execute_play_start`（用户在互动会话里发第一条消息时模型会调它）**无条件调用 `create_world`**。对一个已经存在的世界，这会把 `world.json` 整体覆盖：标题换成模型这次传的，没传的前提 / 世界契约 / 视觉契约清成空串，`createdAt` 重置。

**来历**：git 考古——Rust 端口（761c0399，2026-08-16）搬的当时，TS 的 `play_start` 确实是无条件 `createWorld`；上游同一天在 d1d6d8ec 改成「已存在就 `updateWorld`、没传的保留，不存在才创建」。属于「忠实移植 + 上游后改」，Rust 向 TS 对齐。

**为什么第一批之后变严重**：桥接之前，产品引擎对 Node 腿建的世界是看不见的——再调 `play_start` 只会在 `worlds/<id>` 另起一棵树（分叉，但不毁数据）。第一批之后它认得了，根解析器把 `world.json` 的写入指向 `works/<id>/source`——于是用户在产品引擎上对这类会话发的第一条消息，就会把 Node 腿写下的世界定义覆盖掉。必红验证的报错信息直接摆出了后果：

```
标题不得被模型这次传的换掉：{"title":"模型另起的标题","premise":"","createdAt":"<现在>",…}
```

**修法**：与 TS 现行形态一致——世界已存在 → `update_world`（前提 / 契约传了就用传的，没传保留；标题与 `createdAt` 不动）；不存在 → 照旧创建。顺带对齐了模式优先级：TS 是「会话选的玩法，其次模型传的，再次现有世界的，最后 open」，端口写反了前两个（模型传的优先）——用户在界面上选了「点着玩」，模型传个 `open` 就能盖掉。

**测试**（`play_start_existing_world_tests`，4 条）：Node 腿建的世界在产品引擎上 `play_start` 后标题、前提、`createdAt` 原样、`updatedAt` 刷新、不另起 `worlds/`、转录不动；传了的字段替换、没传的保留；会话选的玩法优先于模型参数；新世界仍按参数创建。**变异**：把两处改回旧行为 → 三条红（新世界那条照旧绿）。

**教训**：桥接存储根会把「另一条腿写下的文件」带进本腿的写入范围——此前无害的「写覆盖」在这一刻变成跨腿的数据破坏。做这类桥接时，要顺着新可达的文件把本腿所有写入点过一遍，而不只是读面。按这句话把产品引擎的写面过了一遍：生产代码里 `create_world` 的唯一调用方就是 `execute_play_start`（已修）；其余写面要么是追加写（转录、事件）、要么是回合语义内的整文件写（当前状态、场景投影）、要么是 PUT 语义（配图设置、插图清单条目）、要么是用户主动的检查点 / 变体保存与还原——没有第二处会整份覆盖另一条腿写的文件。既有的端到端用例（e2e 236 条）与对跑二进制（17 条）在修复后全绿。
