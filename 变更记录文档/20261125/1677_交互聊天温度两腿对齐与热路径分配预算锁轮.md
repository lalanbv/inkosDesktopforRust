## 一、交互聊天温度（两腿同改）

### 取证（修复前，实跑）

| 场景 | Node 腿 | 产品引擎（真实二进制） |
|---|---|---|
| 服务项未配温度 | 请求体不带 `temperature` | 恒发 `0.7` |
| 服务项配 0.3 / 顶层 1.4 | 仍不带 | 仍 `0.7` |
| 模型卡固定温度 = 1（kimi-k2.5） | 不带 | `0.7`——上游只接受 1，**每个聊天请求都会被 400 拒绝** |

- 界面对这项设置的承诺是「随机性（可选）… 模型默认 / 使用默认」（`ServiceDetailPage`）。两腿都没兑现：Node 腿完全无视，产品引擎写死。
- **勘误**：上一轮报告与 1671 号记录写「Node 腿随配置并按模型卡钳制」——那是 `client.chat()`（管线工作调用）的行为；交互聊天走 pi 传输（`guardedPiStream`），不经过它。用进程内探针打上游抓请求体才看清。又一例「读代码推断的行为要用实跑核实」。
- 产品引擎此前没有任何一处消费模型卡的固定温度（`InkosModel.temperature` 零读者）。

### 契约

交互聊天（`POST /api/v1/agent`）的 `temperature`：所选服务项配置了就发；没配置就不发（用模型默认）；模型卡标了服务端固定温度的按卡钳制；未指定时不替调用方 invent 一个值。显式选了服务时只看该服务项自己的配置——顶层 `llm.temperature` 是「所选服务」的镜像，不能套到别的服务上。

### 实现

- **产品引擎**：`ChatCompletionParams.temperature` 由必填 `f64` 改 `Option<f64>`（`None` = 请求体不带该键，chat / responses 两种形态）；模型四层解析（`resolve_agent_model_override`）随覆盖一起给出命中服务项的温度；`RouterLoopChat` 不再写死；传输层漏斗 `stream_chat` 统一按模型卡钳制（`lookup::clamp_temperature_for_model`，全量模型卡逐个核对与 `lookup_model` 同序；不需要钳制时零分配、原样借用）。
- **Node 腿**：`/api/v1/agent` 的四层模型解析各自给出命中服务项的温度 → `clampTemperatureForModel`（从 `provider.ts` 导出）→ 经会话配置 `temperature` 传给 pi 传输。缓存里的 Agent 跨请求复用，所以温度读缓存项而不是闭包里首次请求的 `config`，并每次请求刷新。

### 机制化与验证

- 两腿共用对照表 `packages/studio/src/__tests__/golden/chat-temperature-parity.json`（7 行）：Node 腿 `chat-temperature.flow.test.ts`、产品引擎 `tests/chat_temperature.rs`（全量路由 + 回环上游抓请求体）读同一文件逐行断言。另有一条 Node 用例锁「同一会话里改了随机性，下一个请求用新值」。
- 变异（逐处改坏 → 变红 → 逐字节还原）：Node 腿 7 处（会话拿不到温度 / 不钳制 / 层 1、层 2 不取温度 / 流选项不带 / 读闭包旧值 / 去掉每请求刷新）；产品引擎 7 处（回到恒发 0.7 / 层 1、层 2 不取温度 / 漏斗不钳制 / 不查卡 / 未指定时凭空给 0.7 / 请求体带 `null`）。全部咬住。
- 真实二进制：重建后 7 个场景与 Node 腿逐项一致（不发 / 0.3 / 0.3 / 不发 / 1 / 不发 / 1）。

`benches/hot_paths.rs` 新增 `iter_budgeted`：每条基准的工作负载先计量（取 5 次最小值，滤掉别的线程上的零星分配）并断言预算，再交给 criterion 计时。预算表 `ALLOC_BUDGETS` 没登记即 panic——新增基准必须同时登记时间基线与分配预算。两遍独立计量 32 条逐项相同。

## 三、检索热路径：`book_search/warm_300ch`

量化一上来就暴露：热路径（磁盘投影已建、内容未变）单次 **254,279 次分配 / 32.7 MB**，与冷路径 253,067 只差一次落库；时间 20.76 ms（冷路径 32 ms）。

- 根因：`replace_scope` / `replaceScope` 先对**全部**文档分词，再逐个比内容哈希；未变化文档的分词结果被整个丢掉。基准注释写的「content_hash 全跳」只跳过了落库。Node 腿（2.0 基底）同形——忠实移植。
- 修法：内容哈希只覆盖 kind/source/title/body/metadata，不含分词结果，所以先比哈希、只对变化的文档分词。两腿同改；检索结果不变。
- 结果：单次分配 254,279 → **1,679（−99.3%）**，临时内存 32.7 MB → 213 KB；时间 20.76 ms → 2.48 ms（门禁工况基线，**−88%**；静默时 1.99 ms）。
- 验证：两腿各一条回归测（测试用计数器证明未变化文档零分词：首次全量 / 原样重放 0 / 改一篇加一篇 2 / 元数据变化 1），变异（改回全部重做）两腿都变红。
- 基线：`scripts/bench-baseline.json` 只定点更新这一条（不整表刷新，避免把别的基准的噪声洗进基线）。先登记静默值 1.99 ms，门禁工况下量到 2.48 ms（+24.9%，离 30% 阈值太近）→ 改用门禁工况的测量值；复跑 2.11 ms（−14.8%）。

## 八、教训

1. **「另一条腿的行为」不能靠读代码推断**。「Node 腿随配置并按卡钳制」是我上一轮读 `provider.ts` 得出的结论，交互聊天根本不走那条路。定契约前先在两条腿上把同一条请求实际发出去看载荷。
2. **量化是找问题的手段，不只是验收**。32 条分配数字一出来，热路径与冷路径几乎同量级这一异常自己跳出来——它此前被一条写着「全跳」的注释盖了三个多月。
3. **基线要取门禁工况的测量值**。静默值做基线会让门禁在正常负载下逼近阈值（+24.9% / 30%），变成假红源。
4. **编辑大文件时逐行核对 diff**。本轮一次编辑手滑把一条删除语句的两个占位符对调了（会让消失的文档删不掉），靠 `git diff` 逐行过才当场抓到。
5. **并行会话的 worktree 名是定号的信号**：`wt1676` → 对方要做 1676；同文件在途时先落地提交，让对方在其上合并，而不是用未提交改动堵住对方的 cherry-pick。
