### B. 回合 `try` 之前的失败在缓存里留残留（`packages/core/src/agent/agent-session.ts`）

- 机理：回合 try 之前有会抛错的步骤——送达账本核对回执（回执指向的修订不存在 → `ARTIFACT_NOT_FOUND`）、转录落盘、`startEpisode`（episode 存储 I/O）。它们排在改动内存**之后**：续投路径已把用户 / 动作消息推进 `agent.state.messages`、已开 episode；之后的 `agent.subscribe` 只在回合的 `finally` 里解除。
- 后果：下一次请求在同一缓存项上再叠一层订阅（同一事件落盘两遍、用量 `recordChatUsage` 记两遍）、续投交换在模型上下文里出现两次；`request_started` 没有关档；而 `removeCachedAgent` 对 `currentEpisode` 非 null 的缓存项**拒收**、TTL 清理也只清 `currentEpisode === null` 的——整个会话的 Agent 缓存到进程重启都带着残留。
- 修法：会抛错的步骤一律排在改动内存之前（回执核对 → 转录事件 → 送达状态落盘 → 推进 Agent 记忆），`startEpisode` 单独包住；任何一步失败走 `abortPreparation`——与回合 catch 同一收尾（`request_failed` 关档 + 丢弃缓存项）。回合 catch 改用同一 `failRequest`。转录事件顺序不变。
- 非续投路径同样受益（送达状态落盘失败也会把 episode 钉死）。

## 七、教训

1. **镜像文案必须从 Node 腿实跑取原话**。手写的 V8 TypeError 镜像与 `"Unexpected token"` 全部与实跑不符，潜伏三个多月；两腿一致的错误形态只有在双端实跑对照时才暴露。
2. **「韧性回归」不等于正确行为**。产品引擎把非对象根的 500 钉成了防 panic 的正确结果，却没有人验证 Node 腿在同一输入上是 200 假成功——又一例「双端同为 XX 须双端行为级验证」。
3. **会抛错的步骤排在改动内存之前**；否则需要为每一步写回滚。`removeCachedAgent` 拒收带 episode 的缓存项，使任何「开了 episode 之后才失败」都会把会话缓存钉死。
4. **类型检查要在测试文件写完之后跑**；会话内「已通过」的结论有时效。
5. **夹具自检**：`.env` 存在会被产品引擎识别成 env 配置形态（守卫判 Missing）；手写单行 JSON 容易括号错位——先用 `JSON.stringify` 生成并打出来看。
6. **「同一仓路径串 + cp」之外的新误报**：把含 `apiKey` 字面量的测试值写进测试文件会被 Mimosa 拦（值无关），一律 env 注入 + 非凭据回退（既有惯用形）。
