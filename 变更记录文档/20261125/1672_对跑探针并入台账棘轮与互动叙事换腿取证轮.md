## ③ 互动叙事换腿取证（1668 号立案）

问题：同一个项目根，产品引擎与 Node 回退腿各自读写互动叙事（interactive world），换腿之后对方创建的世界还读得到吗？

**方法**（对跑二进制里的 `interactive_world_storage_roots_duel`，真跑、进台账）：同一项目根下，两腿**各自原生**创建一个世界——产品引擎走自己的写入面（`play::create_world` / `ensure_run` / 图谱库 / `append_transcript_turn` / `save_current_state`）；TS 腿走 core 自己的 `PlayStore` / `createPlayDB`（`tests/strangler_duel/seedPlayWorld.mjs`，与 TS 腿同一份写入代码，不手搓夹具）。然后起两腿互读、迁移、迁移后再写。

| 步骤 | 产品引擎原生的世界 | TS 腿原生的世界 |
|---|---|---|
| ① 迁移前 | 产品引擎 200（标题、1 轮转录）；TS 腿 **404 `PLAY_WORLD_NOT_FOUND`** | TS 腿 200；产品引擎 **404 `PLAY_WORLD_NOT_FOUND`**（④ 对齐前是 200 空壳） |
| ② TS 侧旧数据迁移后 | 产品引擎照常；TS 腿按 works 清单认出了世界，却 **404 `PLAY_RUN_NOT_FOUND`** | 产品引擎仍 404（迁移是单向的 legacy → works） |
| ③ 迁移后再写 | 产品引擎追加一轮 → 自己看到 2 轮，TS 腿仍 404 | TS 腿追加一轮 → 自己 2 轮，产品引擎仍 404 |

文件系统面同样钉住：产品引擎写 `worlds/<id>/`、不写 `works/`，新建的运行落 `play-graph.json`、不建 `play.db`；TS 腿写 `works/<id>/source/`、不写 `worlds/`，新建的运行建 `play.db`（sqlite）。

**两层互相独立的差异**：

1. **根不同**：产品引擎读写 `worlds/<id>/runs/<run>`（`play::world_dir` / `run_dir`，没有 works 兜底）；TS 2.0 读写 `works/<id>/source/runs/<run>`（`PlayStore` 经 `workDirectory`，按 works 清单发现世界）。
2. **图谱后端不同**：TS 2.0 的 `PlayDB` 只用 sqlite（`node:sqlite` 建 `play.db`），读取面把「`play.db` 不存在」直接当作「运行不存在」；产品引擎的工厂是「`play.db` 已存在才走 sqlite，否则文件后端 `play-graph.json`」——只在产品引擎上新建的运行恒走文件后端。所以即便是拷贝式的迁移，也救不了 TS 腿对产品引擎运行的读取。

**定性：是缺陷，不在本轮修。**

- 用户可见症状：产品引擎下创建的互动世界，在 Node 回退腿上打开是「不存在」；Node 回退期间创建的世界，回到产品引擎后也是「不存在」。数据两边都还在盘上（迁移是拷贝、原目录保留），没有丢；但任一腿继续往下写，就在自己那棵树上分叉出第二份。
- 不修的理由：修复要先定**存储模型**——产品引擎迁到 works（`works/<id>/source`），还是自动双向桥接。这与书域（`books/` ↔ `works/<id>/source`）是同一个决定；对方 1671 号也把 `cross_write_read` / `full_grey` 两条对跑留在了同一个前提上。读取面单边兜底不是修复：同一个世界 id 会在两棵树上各有一份、状态分叉。
- 定线后的施工输入：
  - 「TS 腿创建 → 产品引擎读」：产品引擎读取面在 `worlds/<id>` 缺席时回退读 `works/<id>/source`；图谱快照已经支持「`play.db` 在位即走 sqlite」，这一层不用动。
  - 「产品引擎创建 → TS 腿读」：TS 读取面要认文件后端的运行（不再把「没有 `play.db`」等同于「运行不存在」），或产品引擎工厂改成新建运行也落 sqlite。后者是一次移植走样——71 号注释称 Rust 工厂是 `createPlayDB` 后端选择的「Rust 等价」，而 TS 腿 1.x 的判据是「sqlite 可用即 sqlite」、2.0 是恒 sqlite，端口写成了「`play.db` 已存在」。

现状钉测试的断言写的就是上表。它不是为了认可这个行为：存储模型定线那天它应当变红，断言改成「互读可见」。

## ④ 读取面对齐：不存在的世界回 404

取证时发现产品引擎对不存在的世界/运行照样回 200，只是 `title: null`、空转录、空图。git 考古：产品引擎的读取面是 2026-08-16 移植的（803482d0），当时 TS 对不存在的世界就是回 200（`loadWorld(...).catch(() => null)`）——忠实移植；上游 2.0 在 2026-09-25（7e60e13f）改成 404 `PLAY_WORLD_NOT_FOUND` / `PLAY_RUN_NOT_FOUND`，产品引擎没跟。属于「忠实移植 + 上游后改」，产品引擎向 TS 对齐。

为什么值得修而不只是记账：空壳会把「数据其实在另一棵树上」伪装成「一个全新的空世界」。界面看到空世界，接着往里写，就在错误的树上分叉出第二份。

- 世界不存在 → `404 {error:{code:"PLAY_WORLD_NOT_FOUND"}}`；运行目录不存在 → `404 {error:{code:"PLAY_RUN_NOT_FOUND"}}`。响应体与 TS 同形（不带 message）。
- 「运行是否存在」的判据两腿不同：TS 看运行目录里有没有 `play.db`，产品引擎新建的运行没有这个文件，所以按运行目录判。
- 前端三个消费方对 404 都是静默回落（`PlayHud` 注释写明「会话可能还没有落盘的世界，留 null 渲染空状态」；`ChatPage` catch 后置空；`ToolExecutionSteps` 轮询到非 2xx 即重试），而且它们本来就必须处理 404——TS 腿一直回 404。
- 差分器的 `ENDPOINTS` 严格清单里有一条 `/api/v1/play/runs/nonworld/nonrun`，但门禁当前跑的是「三域活体分歧报告」模式，不执行这份清单；用它跑了一遍，共享面 86 对比 0 分歧。

## ⑤ 过程里的四件事

**扫描器的判定依赖文件上下文。** 把真实二进制的启动命令（`cargo_bin` 取 `PathBuf` 再 `Command::new`，与 1669 号已落库的 `llm_config_duel.rs` 逐字相同）加进 `strangler_duel.rs` 时，Mimosa 三种写法（内联单行、内联换行、无参数小函数里的两行）一律按「命令注入」拦截；同样两行放进新的支撑模块文件则放行。才有了 `tests/strangler_duel/engine_bin.rs`。同理，公共夹具拆分时只要把原有的 `apiKey` 夹具键或 `api_key: "duel-key".into()` 那行挪进被替换的块就会被拦——改成原地插函数边界，那两行一个字节没动。

**播种器的参数顺序错了一次。** 脚本约定「命令 → 项目根 → 世界 id」，Rust 侧两次传反；第二次的报错是「Resource ID contains unsafe path characters」，看着像 id 字符集问题，其实是项目根路径被当成 id 去过了 schema。

**一条旧测试钉着旧行为。** e2e 的 `get_run_reads_sqlite_backend` 夹具是「有运行、没世界」并断言 `title == Null`。夹具改成先建世界；顺手让它更有判别力——文件后端的夹具图里有两个实体、sqlite 里只有一个，断言实体数为 1 才证明真走了 sqlite（原断言只看 `entities[0].label`，取错后端也过）。

**一处我自己的记错。** 开工时我把「独立二进制的真实二进制用例」写成「没有 RAII 守卫」，其实它自带 `EngineProcess` / `TsSidecar` 两个带 Drop 的句柄。对方 1671 号的立案项「其他测试文件里起真实二进制的用例是否缺 RAII 守卫未核」结论是「无缺口」，它在同一时段补了勘误提交（`eba94cad`）——与本记录的初稿相左，以对方的核查为准，本记录已改正。
