# 1678 号：章文件命名形态与进度——两腿的 durable 进度都认三种章文件形态（旧命名的书书架 500、下一章号回到 1）+ 导出查找表同口径

> 日期：2026-11-25 ｜ 类型：缺陷修复轮（两腿）+ 同族清扫 + 对跑门禁棘轮
> 定位：清偿 1676 号立案的「Node 腿 `resolveDurableStoryProgress` 的一致性守卫只认 `NNNN_`，索引里有裸章号或连字符章时 `GET /api/v1/books` 回 500」。动手前按同族扫了两腿所有「只认正典章文件形态」的地方，一并处理。

## ① 取证（先红）

**Node 腿**（core 新测试修前 3 红 4 绿）：

- 索引里列着旧命名的章（`0001-镜中醒来.md`、`0002.md`、`0003_云涌.md`）→ `getNextChapterNumber` 抛 `Chapter index/files disagree (orphaned=none; missing=1,2)`。书架接口对全部书并行取摘要，一本书抛就是整页 500——1676 号对跑里 sidecar 的就绪探测就是这么失败的。
- 没有索引 → 下一章号回到 1（应当是 4）。这正是 789 号要防的「write-next 重写第 1 章」，当时只修了正典命名。
- bootstrap 把当前章节与 manifest 进度写成 0（应当是 3）。

**产品引擎**（新测试修前 2 红）：

- 没有索引的旧命名书：durable 进度 0、下一章号 1。后果比 Node 腿重——writer 落盘「第 1 章」时按前导章号清同号旧文件（813 号，三种形态同一集合），原有的第 1 章会被清掉。触发条件是索引缺失或损坏的旧命名书。
- 索引里列着旧命名章的情况产品引擎不抛：它没有守卫，索引与文件直接合并。

**导出**（同族扫描时发现的第四处）：

- Node 腿 `buildChapterFileLookup` 只认正典形态：旧命名的章被报成 `missingChapterNumbers [1,2]` 加 `unindexedFiles`，导出以 `CHAPTER_EXPORT_SOURCE_MISMATCH` 拒绝——这样的书在 Node 腿上导不出（修前实跑红）。
- 产品引擎的导出是宽容的（旧命名章本来就导得出），但查找表是「目录序首个命中」：同章双形态并存时导出哪一份取决于目录顺序，旧稿会被当成正文导出去。

## ② 同族扫描

两腿所有只认正典 `NNNN_` 的章文件认定：Node 腿 `state-bootstrap.ts` 两处（进度守卫、bootstrap 的容忍版进度）、`export-artifact.ts` 一处；产品引擎 `state_bootstrap.rs` 一处。全部改为与索引重建同一个集合——Node 腿用共享的 `chapterFileNumber`，产品引擎用 `leading_number`（845 号立的那把尺子）。

## ③ 修法与取舍

### 进度守卫（Node 腿 `resolveDurableStoryProgress`）

- **「缺文件」查三种形态**：索引里列着的章，任何一种形态在就算有。
- **「孤儿」仍只看正典形态**，没有扩大。正典章是 writer 落盘的形态，索引不认识它等于索引没写上，fail-closed 是对的。旧命名文件不是 2.0 写出来的：807 号之前的回滚删不掉它们，索引之外留着的那种是残留（读侧正典优先，它挡不住正典章）。把残留算成孤儿，会让升级上来的书整页 500。
- **没有索引时**，连续前缀按三种形态算，与索引重建会列出的章同一集合。
- 顺带的口径变化：以前「数字加下划线」开头的任何条目（`0001_x.md.bak`、`0001_notes.txt`）都算章文件，现在只算 `.md` 章文件。章的 `.md` 不在了会报缺文件（更严，是对的）；非章文件不再触发孤儿（更宽，也是对的）。

bootstrap 的容忍版进度（`resolveDurableArtifactProgressTolerant`）同样改法。

### 产品引擎 durable 进度

`load_durable_artifact_chapter_numbers` 的文件集改用 `leading_number`。两腿守卫有无的差异（产品引擎无守卫合并）是 2.0 起就刻意保留的不对称，不动。

### 导出

- Node 腿查找表认三种形态；校验的严格度不变——真缺文件、未入索引的章、同章两个文件，照样拒绝。
- 产品引擎查找表改用读侧同一个裁决（`select_chapter_files`）：同章双形态取正典，不随目录顺序变。择优逻辑抽成接收显式文件名列表的纯函数 `export_chapter_file_lookup`，原因见 ④。

## ④ 测试与变异

- **Node 腿**：core 7 条（进度）+ 4 条（导出）；studio 2 条（真实 `createStudioServer`——带索引与不带索引的旧命名书书架 200、章数 3、详情 `nextChapter` 4、读取面不落盘）。
- **产品引擎**：5 条（durable 进度、下一章号、导出三条）。
- **对跑**：新增 `legacy_chapter_forms_progress_duel`（20 测真跑 18 / 豁免 2，门禁地板 17 → 18）——带索引的三形态混排、不带索引的旧命名书、正典对照书，两腿书架的章数与下一章号一致，读取面不落盘。`destructive_operations_trash_duel` 的夹具改回含裸章号章（1676 号时为绕开这个缺陷改成了正典名）并加书架断言——sidecar 起得来、书架 200，夹具本身就是证据。

变异 6 个，全部阵亡：

| 变异 | 结果 |
|---|---|
| Node 腿守卫的文件集改回只认正典 | 2 条红 |
| Node 腿孤儿检查扩到三种形态 | 1 条红（残留让书打不开） |
| Node 腿 bootstrap 容忍版改回只认正典 | 1 条红 |

## ⑤ 顺带发现（立案）

1. **产品引擎的读取面会写盘**：书架接口 → `get_next_chapter_number` → `bootstrap_structured_state_from_markdown`，把结构化状态四件（`story/state/*.json`）物化落盘；Node 腿的读取面不写。这是 788 号的 ensure 语义，读请求是否该写盘没有定论。对跑里因此要把「回滚之前两棵树就不同的文件」排除出逐字节比较，并钉成恰好这四件。
2. **两腿导出校验的严格度不同**：Node 腿有源一致性校验（缺文件、未入索引、同章重复 → 409 `CHAPTER_EXPORT_SOURCE_MISMATCH`），产品引擎没有——索引里没有的章文件被静默丢弃，缺文件的章被静默跳过。同章双形态：Node 腿拒绝（报重复），产品引擎取正典。本轮只统一了「认哪些文件」，没动「拒绝还是放行」——那是产品判断：改产品引擎等于让原先能导的书变成 409，改 Node 腿等于放宽上游 2.0 的校验。
3. 旧版可选真相文件两腿恢复口径不同（1676 号立案，仍未动）。
