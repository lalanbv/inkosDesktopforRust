# 812 号：表格竖线转义闭环——感知 `\|` 的拆分器与渲染副本转义口径统一

日期：2026-11-02。前置：811 号登记（渲染器把 `|` 转 `\|`，但双侧拆分器朴素按每个 `|` 拆——拆分先于还原，含竖线 notes 会多拆出一列；fork 期渲染副本仅转义竖线不转义换行）。

## 一、现状盘点

渲染副本清单（转义集）：rust `projections.rs`（竖线+换行，810 补齐）/ `agents/chapter_analyzer.rs`（竖线+`\n`，缺 `\r\n`）/ `utils/story_markdown.rs`（仅竖线）；TS `state-projections.ts`（竖线+换行）/ `utils/story-markdown.ts`（仅竖线）。解析器双侧均朴素 `split('|')`。golden leaf.json 含 `\|` 的 6 处全为**渲染**期望（render_hook_snapshot / writer_render_delta_summary_row / render_summary_snapshot / chapter_analyzer_suite）；`render_hook_snapshot` 两用例输入含竖线无换行 → 副本补换行转义不改变 golden 输出。

## 二、修复

**拆分器感知转义**（双侧 `parse_markdown_table_rows` 公共拆分器）：
- TS：`line.split(/(?<!\\)\|/)`（反向预查跳过 `\|`）；`restoreTableCell` 增 `\|` → `|`。
- rust：regex crate 无反向预查，手写扫描 `split_table_row_escaped`（`|` 前一字符为 `\` 不作分隔）；`restore_table_cell` 增 `.replace("\\|", "|")`。
- 固有歧义：值以反斜杠结尾（`a\`）时渲染为 `a\|`，会被当作转义竖线——`\|` 方案的既有边界（上游渲染器选型），记录不改。

**渲染副本口径统一**：TS `story-markdown.ts escapeTableCell` 与 rust `story_markdown.rs escape_table_cell` 补换行 → `<br>`（与 projections 同集）；rust `chapter_analyzer.rs` 补 `\r\n` 先于 `\n` 归一（TS `/\r?\n/g` 同集，否则 CRLF 残留裸 `\r`）。

测试：rust `parse_markdown_table_rows_keeps_escaped_pipes`（转义竖线不拆+还原、未转义照常）+ 投影往返测试 notes 加竖线（`H01|H04` 经 `\|` 往返）；TS 往返测试加竖线 + 转义拆分断言。

## 四、811-812 合并定案

markdown 表格投影的转义/还原契约（双侧同集）：渲染 `|`→`\|`、`\r?\n`→`<br>`；解析按未转义 `|` 拆分，单元格 `<br>`（三形态、忽略大小写）→换行、`\|`→`|`。四份渲染副本（rust 3 / TS 2）转义集一致；两份解析器一致。多行+含竖线 notes（撤回语义）端到端无损。

## 六、教训

1. **转义契约要一次盘点全部副本**：810 修一份、811 修解析、812 补两份渲染+拆分器——分三轮是因为每轮只看到"当下炸的那一处"；盘点副本清单（grep 转义字面）应在第一轮就做。
2. **拆分先于还原**是解析侧的结构约束：还原函数再完备，拆分器不感知转义就先错位；转义方案（`\|`）决定了拆分器必须感知它。
3. golden 覆盖的是渲染期望：解析侧改动不受 golden 保护，须靠往返测试（渲染→解析→原值）自锁。
