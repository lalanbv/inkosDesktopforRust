## ③D1 缺陷定性与修复

**定性（P1，用户可见）**：`branchSession` 成功后调用 `loadSessionDetail` 重拉，但其 merge 守卫 `runtime?.messages.length ? runtime.messages : messages`（任务恢复场景防覆盖本地流式卡的设计）在此把 fresh 的 active 链投影整体吞掉——引擎 head 已移动而 UI 停在弃用路径，用户看到的两轮与实际上下文（一轮）脱节，继续发消息的真实上下文里第 2 轮消失。

**修复**：`loadSessionDetail(sessionId, opts?: { forceReplace?: boolean })`——forceReplace 跳过 baseMessages 守卫用磁盘投影整体替换（task merge 保留；branch 的 409 忙闸保证此刻无在飞请求/任务，强替不打断任何流）；`branchSession` 走强替路径。缺省路径守卫原样（任务恢复守卫回归测试锁定）。

**红绿可证伪**：store 级测试两条（`action.test.ts`）——「branchSession 强替重拉：本地消息被磁盘 active 链投影整体替换」+「缺省 loadSessionDetail 仍保留本地已有消息」；stash 修复旧码红恰 1/40（强替条红、守卫条绿）→ 恢复绿 41/41。jsdom 组件测试对 D1 不可达（store 被整体 mock）——**走查级缺陷要在被 mock 掉的层补测试**是本号的测试布点教训。

## ⑥教训

1. **活体走查是 mock 测试的唯一对偶验证**：D1 恰好藏在组件测试 mock 掉的 store 层——jsdom 全绿 + 真机即断。新 UI 链的「store action → REST → 引擎 → 重拉渲染」全段至少走查一次；测试布点要对着 mock 边界补：哪层被 mock，就在哪层补真桩测试。
2. **重拉型 action 的 merge 守卫是双刃**：防覆盖守卫（任务恢复）与强制刷新需求（分支切换）同一入口冲突——解法是显式 `opts` 通道让调用方声明语义，而非让守卫吞掉所有重拉。
3. **走查的链归属要下到事件层验证**：视图恢复两轮不算证明，`parentSeq=9` 的第三轮事件才是「接在恢复链上」的铁证——UI 断言止步于渲染，链语义断言要到 transcript。
