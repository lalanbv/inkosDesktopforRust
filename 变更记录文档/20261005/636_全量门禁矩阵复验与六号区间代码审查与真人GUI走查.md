## 四、走查抓获的唯一疑点——定性为设计内（备案不修）

**现象**：SIGSTOP 冻结在「POST /chat 已发出但引擎未受理」（内核 backlog）时点停止，解冻后被停轮回复完整落地（UI 渲染+transcript `request_committed` 含 assistant 消息），而 626 号 T2 先例（在飞流中途冻结）是 `request_failed` 无回复。

**定性证据链**：引擎 `abort_agent_session`（session_routes.rs）只对 `running_agent_sessions` 注册表中**已受理在飞**的 loop 置 abort_flag；请求未被受理时注册表无条目 → abort 返回 false no-op → 解冻后请求诚实执行完毕（mock 零延迟先于 abort 被处理）。TS 侧 server.ts L5695 同构语义——**双端设计内，非移植漂移非回归**。前端 624 守卫（chatAbortedAt）挂 catch 拒绝路径，本场景请求成功完成故不触发；前端会话刷新回显磁盘真实状态（UI=磁盘自洽，与 reload 后一致）。

**与 626 号 T2 不矛盾**：后者冻结时 loop 在飞（注册表有条目）→ abort 生效 → request_failed。两者分别覆盖 abort 契约的两半。

**备案项**：abort 契约当前只覆盖「已受理轮」；「排队未受理轮」的停止在引擎恢复后会完整执行并回显。触发窗口=引擎卡顿/重启恢复期且用户恰在该窗口点停止，后果轻（回复最终出现、无数据损坏、无错误噪音）。若未来要收敛，方向=引擎受理请求时检查「会话级 pending-abort 标记」（abort 时落标记、受理时先查再决定执行）——双端同改，另号立项。

## 七、教训

1. **先重建再判读第四次实证**（623/628/632 后）：commit 时间戳晚于二进制构建时间=二进制不含 HEAD，活体套件红先查构建新鲜度。
2. **abort 契约的受理边界**：取消语义只覆盖已被调度体接管的执行；排队态请求的取消需要 pending-abort 标记机制，两半契约要在设计文档里写实（本次靠冻结法走查抓出边界并定性）。
3. **冻结法两种形态是两个测试点**：流中冻结测在飞取消（626 T2），backlog 冻结测受理边界（本号 T4 疑点）——同技法不同冻结时机覆盖 abort 契约两半。
4. **GUI 自动化坐标纪律**：clip 截图估算坐标会错位，坐标点击前必取 getBoundingClientRect；locator actionability 超时时 cua 坐标路径是合法降级（仍是真实用户输入）。
