## 一、测量环境与方法

- 二进制：engine-rs release 构建 `inkos-engine-server`（29MB）
- fixture：`gen-perf-fixture.py` 生成 60 章（3.1MB）/ 500 章（26MB）
- 方法：production bin 直启 + 轮询 /api/v1/health 计就绪毫秒；`ps -o rss` 采样空闲、30 轮查询后、export 大载荷后三个时点；Node 对照 = studio api server（tsx，164 号回退形态）

## 二、结果（release 引擎）

| 指标 | 60 章 | 500 章 / 26MB |
|---|---|---|
| 冷启动至 health 就绪 | 24ms | **25ms** |
| 空闲 RSS | **11MB** | **11MB** |
| 30 轮 books+chapter 查询后 RSS | 14MB | 14MB |
| export TXT 后峰值 RSS | 13MB（载荷 532KB） | 22MB（载荷 4.4MB） |

**Node sidecar 对照（500 章，同负载）**：空闲 RSS **47MB**（tsx 运行时开销）——Rust 引擎为 **1/4.3**，且冷启动同为数十 ms 级。

## 三、结论

1. **无优化必要**：内存与启动均远优于桌面应用常见水位；export 峰值增量（+11MB）与载荷同量级，属瞬时分配，未见泄漏信号（多轮 RSS 稳定）。
2. Rust 迁移收益有了量化注脚：相对 Node 回退形态，常驻内存降至 ~23%，叠加 263 号安全性升级与 267 号冷启动数据——"取其精华弃其糟粕"在资源维度可举证。
3. 与 268 号（debug 冷启动）合并阅读：debug/release 启动毫秒数几乎一致——启动路径非计算受限，为 213 号"稳态延迟"补充了启动维度。
