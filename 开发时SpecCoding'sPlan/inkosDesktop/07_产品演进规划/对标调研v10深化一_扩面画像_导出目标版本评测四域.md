## K. 文档导出与生成工程（6 款 + 2 简提）——对应 R50 批二 docx

### K1 OOXML / ECMA-376（开放标准，ISO 29500）

- 定位：docx 的规范本源（Office Open XML WordprocessingML）。
- 核心机制：docx=OPC（Open Packaging Conventions）ZIP 包；最小包三目录（`_rels`/`docProps`/`word`）+ 唯一必需件 `[Content_Types].xml`；正文=`word/document.xml` 的 `w:body` 内 `w:p/w:r/w:t` 段落-文本运行-文本三层层级；样式（标题层级/字族）走 `word/styles.xml` 的 styleId 引用；中文面=`rFonts` 的 `w:eastAsia` 字族声明。
- 判定：最小集手写路径的**规范依据**——本仓 R50 批二按「4 part 最小包」落地（Content_Types/.rels/document/styles），标题层级=卷 Heading1/章 Heading2，`w:eastAsia` 声明中文字族（宋体）保开档观感。**采**（作为标准件，非依赖）。

### K2 docx（npm，dolanmiu/docx）

- 定位：JS 生态 docx 生成事实标准库（声明式 API：Document/Paragraph/TextRun，Packer 产 blob）。
- 核心机制：全功能覆盖（表格/列表/页眉页脚/编号/图片）；序列化器自研 XML 产线。
- 判定：**不采**。理由：①本仓需求=标题层级+正文段落最小集，23 个传递依赖换 4 个 XML part 手写面不划算（audit:npm 供应链面新增）；②双栈纪律要求 Rust↔TS 镜像——引入 JS 库=TS 腿走库、Rust 腿手写，duel 逐位比对通道被打破（库产 XML 的空白/属性序不受本仓控制）；③手写=双端同一纯函数镜像（golden 可对拍）。若批三做列表/表格再评估（届时功能面超手写性价比）。

### K3 docx-rs（bokuweb/docx-rs）

- 定位：Rust 生态 docx 生成 crate（声明式宏 API）。
- 判定：**不采**。与 K2 同族理由（Rust 腿引库则 TS 腿无法逐位镜像）；且 crate 供应链进 audit:rust 面。手写路径下两端都不引。

### K4 pandoc（开源，Haskell，~38k★ 量级）

- 定位：万能文档转换器事实标准（「格式矩阵全域覆盖」的参照系）。
- 核心机制：内部 AST（Pandoc AST）为中心——解析器族→AST→写出器族；格式对=笛卡尔积而非点对点适配；扩展系统（`markdown+hard_line_breaks` 形态）。
- 判定：**改造采（架构思想）**——「AST 中心」与本仓导出面同构：章集合投影（标题层级/卷分组/章过滤）已是事实 AST，docx/md-zip/md/txt 是四个写出器。R50 批二的 `document.xml` 生成纯函数即第五写出器；不引入 pandoc 本体（体积/调用形态/单机桌面定位三不合）。

### K5 python-docx（开源，Python 生态 docx 操作标准）

- 定位：读改写 docx 的成熟库（OpenXML 包装层）。
- 判定：**不采**（Python 依赖面与本仓无关）；仅作「OOXML 裁剪集」的对照锚——其 API 面证明 docx 的常用子集=段落/样式/表格三族，佐证本仓最小集选型（前两族）合理。

### K6 Scrivener Compile（商业，v8 A1 已画像，本轮 Compile 面深化）

- 定位：写作软件导出管线黄金标准（Compile 面非 export 面）。
- 核心机制：Compile=**格式链**（章标题模板/分隔/前缀后缀）×**内容过滤**（章勾选/草稿含否）×**输出格式**三轴正交；1645 号已按「语义子集」落地（chapter_filter=Scrivener 章过滤语义）。
- 判定：**已对齐（子集）+ 改造采（样式轴深化挂批三）**——docx 落地后样式链（标题模板/分隔符配置）为批三候选，NovelCrafter 2026-01「List support for Word export」佐证导出面持续迭代是行业常态。

### K 简提

- **mammoth**（docx→HTML 语义转换）：读方向件，本仓导出只有写方向，**不采**备案。
- **LibreOffice**（开源办公套件）：docx 全兼容参照系；仅作验收对照（活体开档测试对象之一），**不采**。

## L. 写作目标与习惯追踪（6 款 + 2 简提）——对应 R51

### L1 NaNoWriMo 官方统计（商业活动平台，形态标杆）

- 定位：写作目标追踪的原型叙事（50,000 词/30 天挑战）。
- 核心机制：①**日节奏线**（50k÷30=1,667 词/日）与个人实际 pace 的双线对比；②进度条（当前/目标）；③「按当前 pace 的预计完成日」投影。
- 判定：**采（语义）**——R51 进度面=目标 vs 实际+节奏投影（`expectedFinish` 纯函数）；**不做**挑战/社区/字数验证面（单机定位）。

### L2 Narrative Word Count Tracker / WriteO（独立追踪工具，商业免费）

- 定位：NaNoWriMo 官网社区功能衰退后的替代追踪器生态（Reddit 线程实证的需求外溢）。
- 核心机制：日字数记录+**streak（连续达成天数）**+最 productive 时段分析+自定义日目标（WriteO 另有 session 跟踪/WPM）。
- 判定：**采（streak 语义）**；「最 productive 时段」依赖 session 级数据（本仓无 session 概念）**不采**；WPM **不采**。

### L3 GitHub contribution graph（工程惯例件）

- 定位：日历热图的事实标准形态（53 周×7 日格子，五档色阶，hover=当日明细）。
- 判定：**改造采（月历先行）**——中文网文写作者习惯（起点作家助手形态）更贴**当月日历格**而非年热图；R51 先做月历（日格=当日净增字数+达成着色），53 周年热图挂观察（数据积累满一年才有观感）。

### L4 Habitica（商业，游戏化习惯追踪标杆）

- 定位：RPG 化习惯养成（经验/金币/装备/宠物）。
- 判定：**不采**——v8 深化三已裁定「不做积分/徽章游戏化」，本轮横扫后维持：游戏化与「写作工具的专业感」定位冲突（Scrivener/Ulysses 无一游戏化）；streak 数字显示（L2 语义）已覆盖「坚持反馈」需求的最小面。

### L5 4thewords（商业，游戏化写作）

- 定位：打怪写作（字数达标击败怪物）。
- 判定：**不采**（同 L4 判定，且其核心机制=强制写作 session，与本地自由写作节奏不合）。

### L6 Scrivener project targets / Ulysses goals（v8 A1/A2 目标面深化）

- 定位：桌面写作软件的目标面双标杆。
- 核心机制：Scrivener=项目目标+session 目标双层进度条+截止日（deadline 自动算日需求）；Ulysses=每篇/每组目标+日周月滚动统计。
- 判定：**改造采**——R51 形态定案=书级 `targetWords`（顶层键与 targetChapters 同族）+全局日目标+截止日可选（deadline 投影日需求纯函数）；「每章目标」已有 `chapterWordCount` 既有键覆盖（现状=已对齐）。

### L 简提

- **社区表格模板**（Facebook 作家群 Excel/子弹笔记）：手工 log 日字数+公式算 pace——证明「日字数记录+投影」是真实最低门槛需求，佐证 R51 账本设计方向。
- **obsidian-heatmap 类插件**：年热图在笔记工具的插件形态——L3 年热图观察项的生态佐证。

## M. 版本历史与 diff 面（6 款 + 1 简提）——对应 R53

### M1 Obsidian File Recovery（官方核心插件）

- 定位：笔记工具版本恢复的标配形态（与本仓章版本 `.versions` 最同构：本地全内容快照）。
- 核心机制：定时全内容快照（非 diff）+保留窗（默认 7 天）滚动清理+命令面板「Open local history」+按文件名搜索+单版本恢复。
- 判定：**已对齐（底座）**——本仓 `.versions/{NNNN}/` 时间戳_来源_uuid 命名+写入/列举/读取/恢复三端点双端在位，机制面等价且**来源标签更细**（manual/agent/revision/regeneration/restore/structure 六源 vs Obsidian 单一自动快照）。保留窗清理策略本仓未做（快照无限累积）——挂 R53 附带观察项（磁盘占用真实反馈后再定）。

### M2 Time Machine for Obsidian（社区插件，dsebastien）

- 定位：File Recovery 的 UI 补位生态（作者自述动机=官方恢复面「basic and clunky」）。
- 核心机制：快照**浏览/步进（prev/next 版本导航）/两版比较**三件套——证明「有快照无浏览面」是普遍缺口，UI 面是独立价值件。
- 判定：**采（UI 形态参照）**——R53=本仓版 Time Machine：历史页挂章详情（版本列表+diff 投影+恢复引导），引擎面零改动（本轮修正#2 的依据）。

### M3 Version Control for Obsidian（社区插件）

- 定位：**主动**版本（intentional snapshots）补充官方**自动**版本。
- 判定：**已对齐**——本仓 manual 来源标签已覆盖主动存版语义；命名版本（Google Docs 形态）不采（版本 ID 已含语义来源，再起名=第二真相源）。

### M4 Google Docs version history（商业标杆）

- 定位：作者面版本历史的最高水位（非技术用户零学习成本）。
- 核心机制：命名版本+「仅显命名版」过滤+恢复=当前内容先成新版本（**恢复不丢历史**）+变更高亮着色。
- 判定：**采（恢复不丢历史语义——本仓 restore 端点已同构，R53 文案强调此点）**；「任意两版比较」是 Google 原生盲区（社区实测只能比相邻版，任意两版要复制文档+Compare Documents 绕行）——本仓 R53 直接做**任意两版 diff**（LCS 纯函数已有），此处**超越标杆**。

### M5 Wikipedia 页面历史 / compare（开源形态）

- 定位：非技术用户的行级 diff 教学范本（百科编辑者的大众化 diff 消费面）。
- 核心机制：任意两版 compare+增删行着色+段级上下文折叠。
- 判定：**改造采**——佐证 diff 面向作者时的呈现纪律：行级 −/+ 着色（本仓 series-backfill-diff 形态）优于字符级花哨高亮；R53 沿用 −/+ 行级即可。

### M6 react-diff-view / diff2html（工程件）

- 定位：React 生态 diff 渲染两大件（diff2html≈HTML 产线、react-diff-view=组件化+unified/split 双视图）。
- 判定：**不采**——R53 需求=行级 −/+ 单视图（M5 纪律），series-backfill-diff.ts 纯函数+简单列表渲染已够；引入 diff 渲染件=样式面+bundle 面新增，split 视图（代码 review 场景）对作者冗余。

### M 简提

- **Scrivener Snapshots 对比**（v8 A1 深化）：排印差分（typographic diff）按字词着色——更细粒度但实现重；R53 行级起步，字级 diff 挂观察。

## N. prompt 评测与用量（4 款 + 2 简提）——对应 R54/R55

### N1 promptfoo（开源 MIT）

- 定位：prompt 评测/回归测试开源标准（CLI+库，红队/评测双面）。
- 核心机制：`promptfooconfig` 四件套（prompts/providers/tests/**assertions**）声明式配置；eval 矩阵（prompt×model×case）跑分；CI 集成防「silent regression」（行为静默回退）。
- 判定：**改造采（形态参照，零引入）**——四件套与本仓既有面一一同构：prompt pack（`{root}/prompt/` 三级覆盖）/providers（服务配置+failover R25）/tests（R8 行为评测锚点）/assertions（LLM-as-judge R17）。R54=promptfoo 的**本地化形态**：版本 artifact+变更后评测门触发，CLI/CI 形态不引入（无 workflow 既定裁定）。

### N2 Langfuse prompt management（开源可自宿，v8 D 类已画像，prompt 面深化）

- 定位：prompt 当代码管理（版本/label/回滚）+观测联动。
- 判定：**改造采（label 语义）**——R54 版本面加 production/draft 双 label（当前生效版=production label 指针，回滚=label 切换而非文件移动）——比纯 append-only 目录多一层指针语义，防「回滚后目录序与生效序不一致」。

### N3 Helicone（开源网关/观测，本轮新增画像）

- 定位：LLM 用量/成本观测代表（软限告警路线）。
- 核心机制：cost alerts 可配阈值+**软限（告警不硬断）**+per key/model/自定义属性过滤粒度+分 key 预算隔离。
- 判定：**改造采（软限语义，R55 蓝本）**——v8 深化三 R55「80% 告警/100% 确认、无计费语义」与 Helicone 软限定位同向；本轮修正=先立用量账本（per-service 数据现状零存在），阈值告警消费账本。硬断（竞品 MLflow AI Gateway 形态）维持不采。

### N4 LiteLLM budgets（v8 D1 预算面深化）

- 定位：预算机制的老牌参照（v8 已画像其路由/failover）。
- 核心机制：per-key/per-model budget+预算耗尽 fallback 链+周期重置。
- 判定：**改造采（周期窗口语义）**——R55 日/月窗口与重置投影纯函数参照；virtual keys 形态**不采**（单机 BYOK 无多租户）。

### N 简提

- **Braintrust / LangSmith**（商业评测平台）：托管评测+数据集管理形态，R54 本地化已覆盖所需面，**不采**。
- **MLflow AI Gateway**：硬限 auto-reject 路线对照锚，**不采**（N3 判定依据）。
