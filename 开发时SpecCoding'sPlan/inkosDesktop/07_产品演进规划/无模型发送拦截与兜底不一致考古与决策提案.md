# 无模型发送的拦截与兜底不一致——考古实测与决策提案（589 号）

- 日期：2026-10-02　类型：决策提案（零代码改动，待裁决）
- 起因：574 号真机走查备案「新会话无模型发消息被前端硬拦，而后端理论上有四层解析可兜底」——两路径行为不一致

## 实测考古（三段，2026-10-02，Node 回退端 4593+walkthrough-mock 4319）

环境：fixture root 的 inkos.json 已配置 `custom:Mock` 服务（baseUrl 指向 mock）+ secrets 有 `custom:Mock: sk-mock`——**用户视角配置是完整的**。

1. **前端**：新会话发消息 → `action.ts:498 if (!get().selectedModel)` 硬拦，错误消息「请先选择一个模型」。用户被引向 575 置顶的自定义服务表单（引导已可用）。
2. **后端直发**（绕过前端，curl POST /api/v1/agent 不带 model 字段）→ **不以「未配置」拒绝**，进入模型解析链后报：
   `AGENT_LLM_ERROR: No API key for provider: openai`（pi-ai 库内部抛出）。
3. **矛盾点**：secrets 里明明有可用的 custom:Mock key——错误却指向毫不相干的 `openai` provider。

## 定性

- Node 回退端 `/agent` 的模型解析链在零显式模型时构造了 **openai 系默认 pi Model 卡**，且 **secrets 的服务配置未参与该解析**（与 Rust 端 `resolve_agent_model_override` 的四层解析——前端显式 → defaultModel → secrets 首个有 key 服务 → 配置端点——**不同构**）。
- 因此前端硬拦**事实上有理**：零配置时后端不能兜底跑通，拦截给出的引导（575 置顶表单）优于后端的晦涩错误。
- 但真实缺陷依然存在：**配置了 custom 服务与 key 的用户，直发得到的是「openai 无 key」这种误导性错误**——配置在场却被解析链无视。

## 选项

| 选项 | 内容 | 代价/风险 |
|---|---|---|
| A | 维持现状（前端拦截+置顶引导），后端错误面不动 | 零成本；但绕过前端的调用方（脚本/未来集成）仍见误导错误 |
| B | Node 端模型解析补 secrets 兜底（对齐 Rust 四层解析语义） | 触及 Node 模型解析链装配（provider.ts 模型卡构造点），可挂 R45 提供方 seam 载体；行为变更=零显式配置从报错变为可用（需确认产品意图：静默用首个有 key 服务是否可接受） |
| C | 最小错误面修复：解析落到默认卡且 secrets 存在可用服务时，错误消息改写为「检测到已配置服务 custom:Mock，请在聊天页选择模型或设为默认」 | 改动小（错误消息构造点），消除误导；不改变行为 |

## 建议

**C 先行**（错误面去误导，低风险）；**B 挂 R45 seam 载体评估**（涉及解析链重构，需先裁决「静默兜底」是否符合产品意图——若裁决为是，A/C 的引导与错误面均可随之简化）。
