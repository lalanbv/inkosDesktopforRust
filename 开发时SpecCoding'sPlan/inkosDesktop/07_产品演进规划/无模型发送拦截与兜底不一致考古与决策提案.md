# 无模型发送的拦截与兜底不一致——考古实测与决策提案（589 号）

- 日期：2026-10-02　类型：决策提案（零代码改动，待裁决）
- 起因：574 号真机走查备案「新会话无模型发消息被前端硬拦，而后端理论上有四层解析可兜底」——两路径行为不一致

## 实测考古（三段，2026-10-02，Node 回退端 4593+walkthrough-mock 4319）

环境：fixture root 的 inkos.json 已配置 `custom:Mock` 服务（baseUrl 指向 mock）+ secrets 有 `custom:Mock: sk-mock`——**用户视角配置是完整的**。

1. **前端**：新会话发消息 → `action.ts:498 if (!get().selectedModel)` 硬拦，错误消息「请先选择一个模型」。用户被引向 575 置顶的自定义服务表单（引导已可用）。
2. **后端直发**（绕过前端，curl POST /api/v1/agent 不带 model 字段）→ **不以「未配置」拒绝**，进入模型解析链后报：
   `AGENT_LLM_ERROR: No API key for provider: openai`（pi-ai 库内部抛出）。
3. **矛盾点**：secrets 里明明有可用的 custom:Mock key——错误却指向毫不相干的 `openai` provider。

## 定性

- Node 回退端 `/agent` 的模型解析链在零显式模型时构造了 **openai 系默认 pi Model 卡**，且 **secrets 的服务配置未参与该解析**（与 Rust 端 `resolve_agent_model_override` 的四层解析——前端显式 → defaultModel → secrets 首个有 key 服务 → 配置端点——**不同构**）。
- 因此前端硬拦**事实上有理**：零配置时后端不能兜底跑通，拦截给出的引导（575 置顶表单）优于后端的晦涩错误。
- 但真实缺陷依然存在：**配置了 custom 服务与 key 的用户，直发得到的是「openai 无 key」这种误导性错误**——配置在场却被解析链无视。

## 595 号再勘误：592 结论勘误+custom 服务边界实锤

592 的「Rust 直接成功」经去 env 重测证伪——592 探针环境带了 `INKOS_LLM_BASE_URL` env（env 层优先于配置解析），去掉后 Rust 零显式直发失败（请求打到缺省 `127.0.0.1:9`）。

**双端真实图景（本轮归因实锤）**：

- Rust 层 3（`resolve_agent_model_override` 层 3）实现完整（secrets 键序→list_models_for_service→首个文本模型→resolve base_url），但 **`custom:*` 服务被排除**：`list_models_for_service` 只查 preset bank（custom 不在 bank → 模型发现为空 → 下落缺省）——`agent_production.rs:3911` 测试锁定该行为；
- Node 第 3 层**支持 custom**（`resolveConfiguredServiceBaseUrl` 读 inkos `llm.services` 的 baseUrl → mock /models 发现模型）——593 标准布局实测成功即为证；
- 结论：**双端不一致方向实锤=Rust 层 3 缺 custom 服务的 baseUrl 感知模型发现**（Node 有、Rust 无）。

**裁决更新**：B 恢复「待评估」，方向已精确——若实施，落点=Rust 层 3 为 `custom:*` 服务补 baseUrl 感知的模型发现（对齐 Node 第 3 层）；影响面=Rust 解析行为变更（custom 服务零显式直发从失败变成功）+层 3 测试更新；593 注销结论中「双端同构」部分勘误为「第 3 层 custom 支持双端不同构」。

## 606 号增补：层 3 stream 偏好双端分歧（精确归因与备案）

605 落地（Rust 层 3 补 custom 感知）后复检发现一处**层 3 偏好的双端分歧**：

- **apiFormat**：双端一致支持（Rust 605 补齐 `resolve_configured_service_api_format`；Node 第 3 层经 `resolveServiceModel` 的 `customApiFormat` 参数支持）；
- **stream 偏好**：**Rust 层 3 尊重服务配置**（`resolve_configured_service_stream` → `stream: Some(false)` 非流式直发），**Node 第 3 层恒流式**（`ResolvedModel` 无 stream 字段；`/agent` 的 `streamFn` 架构恒走 `guardedAgentStream` 流式）——配置 `stream: false` 的 custom 服务用户：Rust 引擎下非流式（按偏好），Node 回退端下流式（忽略偏好）。

**归因**：Node `streamFn` 架构恒流式，层 3 传 stream 偏好需要 agent-session 增加非流式路径（重构，非小改）。

**备案裁决**：Rust 保留尊重配置（正确语义）；Node 层 3 stream 支持缺口**备案**——实际影响为展示层差异（流式 vs 等待完整回复），功能双端均可用；若后续 Node `streamFn` 架构支持非流式，随批补齐。
